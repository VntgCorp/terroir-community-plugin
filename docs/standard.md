# 플러그인 표준

**이 마켓에 올라오는 플러그인이 지켜야 할 것.** 전부 CI 가 검사한다 — 문서와 집행이
갈리지 않게 아래 모든 규칙은 **정본 파일을 가리킨다.**

처음 올리는 사람은 [스킬 제작 방법](authoring.md)의 절차를 따르면 이 표준을 자동으로
만족한다. 이 문서는 **무엇이 규칙인지**만 말한다.

## 정본이 어디 있나

값이 의심스러우면 문서가 아니라 아래를 본다.

| 규칙 | 정본 | 검사 |
|---|---|---|
| 허용 분류 목록 | [`.github/categories.txt`](../.github/categories.txt) | `check-structure.mjs` |
| 이름 문자 규칙 · 설명 길이 상한 | [`.github/scripts/check-structure.mjs`](../.github/scripts/check-structure.mjs) 머리의 상수 | 〃 |
| 플러그인 스키마 | Claude Code 공식 CLI | `claude plugin validate` |
| 버전 올리는 기준 | [버전업 경로](versioning.md) | `check-version-bump.mjs` |

---

## 1. 어디에 만드나

```
plugins/<분류>/<이름>/
```

**정확히 2단계다.** `plugins/` 바로 아래에 플러그인을 두거나, 분류 아래를 한 겹 더
파면 CI 가 떨어뜨린다.

### 분류를 고르는 법

**[`.github/categories.txt`](../.github/categories.txt) 를 연다.** 그 파일에 허용되는
분류 목록과 고르는 기준이 **둘 다** 있다. 이 문서는 목록도 기준도 옮겨 적지 않는다 —
옮기면 분류가 늘 때 이 문서만 뒤처진다.

**분류를 늘리는 것은 플랫폼개발팀만 할 수 있다.** 목록에 없는 분류가 필요해 보여도
직접 만들지 말고 기준에 따라 있는 것 중 하나를 고른다. 정말 필요하면
[마켓을 바꾸는 절차](operations.md)의 분류 절을 본다.

## 2. 무엇을 반드시 두나

```
plugins/<분류>/<이름>/
├── .claude-plugin/plugin.json ···· 필수
├── README.md ····················· 필수
├── skills/<이름>/SKILL.md ········ 필수 (최소 하나)
├── CHANGELOG.md ·················· 두 번째 버전부터
└────────── 아래는 전부 자유 ──────────
    references/ · scripts/ · hooks/ · examples/ · agents/ · commands/ · 그 밖에 뭐든
```

**「유효한 플러그인인가」만 본다. 「어떻게 만들었나」는 묻지 않는다.** 훅·스크립트 같은
실행 코드도 제한하지 않는다 — 대신 설치하는 쪽이 그걸 안다는 전제로 운영한다
([이 마켓은 무엇인가](about.md)).

## 3. 이름

| | |
|---|---|
| 문자 | 소문자 · 숫자 · 하이픈. 정확한 규칙은 `check-structure.mjs` 의 `NAME_RE` |
| 유일성 | **마켓 전체에서 유일하다.** 분류가 달라도 겹치면 안 된다 |
| 일치 | 디렉토리명 == `plugin.json` 의 `name` |
| 금지 | `claude` · `anthropic` 으로 **시작**하면 설치가 안 된다 |

겹치면 **의미를 더하는 suffix** 를 붙인다.

| | |
|---|---|
| ✕ 숫자 suffix | 설치하는 사람이 둘 중 무엇을 고를지 알 수 없다 |
| ✕ 소유자 접두어 | 세션에 `<플러그인>:<스킬>` 로 뜨는데 접두어가 붙으면 두 번 읽힌다. 소유자는 `plugin.json` 이 기록한다 |
| ○ 쓰임을 좁히는 말 | 어떤 범위·대상에 쓰는 것인지를 이름이 말하면 고를 수 있다 |

## 4. 매니페스트

```json
{
  "name":        "<이름>",
  "description": "<한 줄 설명>",
  "version":     "1.0.0",
  "author":      { "name": "<작성자 본인>" },
  "metadata":    { "owner": "<GitHub 핸들>", "team": "<소속 팀>" }
}
```

| 필드 | | |
|---|---|---|
| `name` | 필수 | 디렉토리명과 같다 |
| `description` | 필수 | **설치 전 목록에 보이는 한 줄.** 길이 상한은 `PLUGIN_DESC_MAX` |
| `version` | 필수 | `Major.Minor.Patch`. 처음은 `1.0.0`. 기준은 [버전업 경로](versioning.md) |
| `author.name` | 필수 | **만든 사람 본인.** 남의 이름이나 팀 이름을 적지 않는다 |
| `metadata.owner` | 필수 | **GitHub 핸들.** 사람 이름이 아니라 `@` 뒤에 쓰는 그 핸들이다. 소유 기록과 리뷰 요청에 쓴다 |
| `metadata.team` | 선택 | 소속 팀. 적어 두면 개인이 떠났을 때 누구에게 물을지 남는다 |

`category` 는 **적지 않는다.** 분류의 정본은 디렉토리 위치다. 둘을 다 두면 반드시 갈린다.

## 5. `SKILL.md`

frontmatter 에 `name` 과 `description` 이 있어야 한다.

```yaml
---
name: dockerize
description: 서비스를 컨테이너화할 때 사용. Dockerfile 작성·빌드·레지스트리 푸시 절차를 안내한다.
---
```

**`description` 은 「언제 이 스킬을 써야 하는가」를 적는 자리다.** 무엇을 하는지의 설명을
여기 쏟아붓지 않는다 — 모든 세션의 컨텍스트를 차지하고, 길수록 트리거 판정이 흐려진다.
상세는 본문에 쓴다. 길이 상한은 `SKILL_DESC_MAX`.

스킬 본문을 **잘** 쓰는 법은 공식 `skill-creator`·`plugin-dev` 가 가르친다. 이 표준은
그 내용을 다시 쓰지 않는다 — [스킬 제작 방법 0절](authoring.md#0-먼저--스킬-만드는-법은-공식이-가르친다).

## 6. `README.md`

쓰는 사람이 **설치할지 말지 결정할 수 있을 만큼** 쓴다.

```markdown
# <이름>

한 줄 설명.

## 무엇을 하나
어떤 상황에서 무엇을 해주는지. 결과가 어떻게 나오는지.

## 쓰는 법
호출 예시. `/<플러그인>:<스킬>` 또는 어떤 말을 하면 뜨는지.

## 아는 한계
안 되는 것 · 전제 조건 · 주의할 것.

## 소유자
<이름> (@<GitHub 핸들>)
```

**「아는 한계」를 비우지 않는다.** 품질 심사가 없는 마켓이라, 무엇이 안 되는지를 만든
사람이 적는 것이 유일한 안전장치다.

## 7. 올린 뒤

| | |
|---|---|
| 머지 | CI 만 통과하면 **본인이 머지한다.** 승인 대기 없음 |
| 고칠 때 | `version` 을 올린다. 안 올리면 CI 가 떨어뜨린다 |
| 그 외 | 내리기 · 이관 · 남의 것 고치기는 [마켓을 바꾸는 절차](operations.md) |

## 8. CI 가 보는 것

| 검사 | |
|---|---|
| 분류 | `plugins/` 바로 아래가 허용 목록 안인가 · 그 아래가 정확히 1단계인가 |
| 이름 | 문자 규칙 · 마켓 전체에서 유일한가 · 디렉토리명 == `name` |
| 매니페스트 | `description` · `version` · `author` · `metadata.owner` 가 있는가 · 길이 상한 |
| 파일 | `README.md` 가 있는가 · `SKILL.md` 가 최소 하나 있는가 |
| 스킬 | frontmatter 의 `name` · `description` 존재 · `description` 길이 |
| 버전 | 파일이 바뀌었는데 `version` 이 그대로인가 |
| 조립물 | `marketplace.json` 이 `plugins/` 와 맞는가 |
| 스키마 | `claude plugin validate` 통과 |

**떨어지면 메시지가 고치는 법을 알려준다.** 안 알려주면 그건 CI 의 버그다.
