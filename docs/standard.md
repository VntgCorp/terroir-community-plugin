# 플러그인 표준

**이 마켓에 올라오는 플러그인이 지켜야 할 것.** 대부분 CI 가 검사한다 — 문서와 집행이
갈리지 않게 아래 모든 규칙은 **정본 파일을 가리킨다.** 검사하지 않는 것은 그 자리에 적었다.

처음 올리는 사람은 [스킬 제작 방법](authoring.md)의 절차를 따르면 이 표준을 자동으로
만족한다. 이 문서는 **무엇이 규칙인지**만 말한다.

## 정본이 어디 있는가

값이 의심스러우면 문서가 아니라 아래를 본다.

| 규칙 | 정본 | 검사 |
|---|---|---|
| 허용 분류 목록 | [`.github/categories.txt`](../.github/categories.txt) | `check-structure.mjs` |
| 이름 문자 규칙 · 설명 길이 상한 | [`.github/scripts/check-structure.mjs`](../.github/scripts/check-structure.mjs) 머리의 상수 | 〃 |
| 플러그인 스키마 | Claude Code 공식 CLI | `claude plugin validate` |
| 버전 올리는 기준 | [버전업 경로](versioning.md) | `check-version-bump.mjs` |

---

## 1. 어디에 만드는가

```
plugins/<분류>/<이름>/
```

**정확히 2단계다.** `plugins/` 바로 아래에 플러그인을 두거나, 분류 아래를 한 겹 더
파면 CI 가 떨어뜨린다.

### 분류를 고르는 법

**[`.github/categories.txt`](../.github/categories.txt) 를 연다.** 그 파일에 허용되는
분류 목록과 고르는 기준이 **둘 다** 있다. 이 문서는 목록도 기준도 옮겨 적지 않는다 —
옮기면 분류가 늘 때 이 문서만 뒤처진다.

**분류를 늘리는 것은 플랫폼개발팀만 할 수 있다.** 목록에 없는 분류가 필요해 보여도
직접 만들지 말고 기준에 따라 있는 것 중 하나를 고른다. 정말 필요하면
[마켓을 바꾸는 절차](operations.md)의 분류 절을 본다.

## 2. 무엇을 반드시 두는가

```
plugins/<분류>/<이름>/
├── .claude-plugin/plugin.json ···· 필수
├── README.md ····················· 필수
├── skills/<이름>/SKILL.md ········ 필수 (최소 하나)
├── CHANGELOG.md ·················· 두 번째 버전부터
└────────── 아래는 전부 자유 ──────────
    references/ · scripts/ · hooks/ · examples/ · agents/ · commands/ · 그 밖에 뭐든
```

**「유효한 플러그인인가」만 본다. 「어떻게 만들었나」는 묻지 않는다.** 훅·스크립트 같은
실행 코드도 제한하지 않는다 — 대신 설치하는 쪽이 그걸 안다는 전제로 운영한다
([이 마켓은 무엇인가](about.md)).

## 3. 이름

| | |
|---|---|
| 문자 | 소문자 · 숫자 · 하이픈. 정확한 규칙은 `check-structure.mjs` 의 `NAME_RE` |
| 유일성 | **마켓 전체에서 유일하다.** 분류가 달라도 겹칠 수 없다 |
| 일치 | 디렉토리명 == `plugin.json` 의 `name` |

### 이름이 겹치면

**먼저 온 이름이 이긴다. 뒤에 오는 쪽이 자기 이름을 바꾼다.**

```
  내가 올리려는 이름이 이미 있다
        │
        ├─ ✗ 남의 플러그인을 지우거나 이름을 바꾸지 않는다
        │     그 소유자의 승인이 필요하고, 쓰던 사람의 설치가 끊긴다
        │
        └─ ○ 내 이름에 쓰임을 좁히는 말을 더한다
```

| | |
|---|---|
| ○ 쓰임을 좁히는 말 | `curriculum-fe` · `curriculum-sales` — 어떤 범위·대상에 쓰는지를 이름이 말하면 설치하는 사람이 고를 수 있다 |
| ✕ 숫자 | `curriculum-2` 는 정보가 없다. 둘 중 무엇을 설치할지 못 고른다 |
| ✕ 소유자 접두어 | 세션에 `<플러그인>:<스킬>` 로 뜨는데 접두어가 붙으면 두 번 읽힌다. 소유자는 `plugin.json` 이 기록한다 |

**같은 일을 하는 스킬이라면 이름을 바꾸기 전에 한 번 묻는다** — 이미 있는 것을 쓰면
되는지, 아니면 그쪽에 기여하는 편이 나은지. 비슷한 스킬이 둘이면 설치하는 사람이
매번 고민한다. 연락처는 `plugin.json` 의 `metadata.owner` 에 있다.

올리기 전에 겹치는지 보는 법은 [스킬 제작 방법](authoring.md)에 있고,
`/skill-market:new` 는 이 조회를 자동으로 한다.

## 4. 매니페스트

```json
{
  "name":        "<이름>",
  "description": "<한 줄 설명>",
  "version":     "1.0.0",
  "author":      { "name": "<작성자 본인>" },
  "metadata":    { "owner": "<GitHub 핸들>", "team": "<소속 팀>" }
}
```

| 필드 | | |
|---|---|---|
| `name` | 필수 | 디렉토리명과 같다 |
| `description` | 필수 | **설치 전 목록에 보이는 한 줄.** 이 플러그인이 무엇을 위해 있는지만 적는다 — 하는 일은 README 에. 길이 상한은 `PLUGIN_DESC_MAX` |
| `version` | 필수 | `Major.Minor.Patch`. 처음은 `1.0.0`. 기준은 [버전업 경로](versioning.md) |
| `author.name` | 필수 | **만든 사람 본인.** 남의 이름이나 팀 이름을 적지 않는다 |
| `metadata.owner` | 필수 | **GitHub 핸들.** 사람 이름이 아니라 `@` 뒤에 쓰는 그 핸들이다. `CODEOWNERS` 의 소유자와 같아야 한다 — 다르면 CI 가 떨어뜨린다 |
| `metadata.team` | 선택 | 소속 팀. 적어 두면 개인이 떠났을 때 누구에게 물을지 남는다 |

`category` 는 **적지 않는다.** 분류의 정본은 디렉토리 위치다. 둘을 다 두면 반드시 갈린다.

## 5. `SKILL.md`

frontmatter 에 `name` 과 `description` 이 있어야 한다. `when_to_use` 는 선택이다 — 언제 부르는지를 적을 때 여기에 둔다.

```yaml
---
name: meeting-notes
description: 회의 메모를 안건별로 정리해 바로 공유할 수 있게 한다.
when_to_use: 회의가 끝나고 메모나 녹취를 정리하려 할 때. 예 "회의록 정리해줘", "이 메모 안건별로 나눠줘".
---
```

| 필드 | 적는 것 | 적지 않는 것 |
|---|---|---|
| `description` | 이 스킬이 **무엇을 위해 있는지** 한 문장 | 하는 일 나열 · 절차 순서 · 쓰는 도구 목록 · 트리거 문구 |
| `when_to_use` | 언제 부르는지 — 상황 · 트리거 문구 · 예시 요청 · 쓰지 않는 경우 | 하는 일 · 절차 |

하는 일 · 절차 · 도구는 **본문**에 쓴다.

```
✕ description: 문서 유형을 정하고 목차를 짠 뒤 용어집을 만들어 그 표현으로 쓰는 스킬. "가이드 써줘" 류 요청에 발동.
○ description: 한국어 기술 문서를 검증된 표현과 정해진 구조로 일관되게 쓰게 한다.
  when_to_use: 사용자용 문서를 새로 쓰거나 크게 고칠 때. 예 "가이드 써줘", "README 정리".
```

**왜 나누나.**

- 두 필드는 모든 세션의 스킬 목록에 실려 컨텍스트를 차지한다. Claude 는 이것만 보고 스킬을
  부를지 정한다. 절차까지 넣으면 본문과 같은 내용이 두 벌이 되고, 고칠 때 한쪽만 바뀐다
- Claude Code 는 두 필드를 합쳐 1,536자에서 자른다. `description` 이 앞에 붙으므로,
  짧아야 뒤의 트리거 문구가 잘리지 않는다

길이 상한은 `description` 에만 있다 — `SKILL_DESC_MAX`.

Claude Code 공식 문서는 `description` 을 「무엇을 하고 언제 쓰는지」로 설명한다.
**이 마켓에서는 이 절을 따른다** — 언제는 `when_to_use` 로 뺀다.

스킬 본문을 **잘** 쓰는 법은 공식 `skill-creator`·`plugin-dev` 가 가르친다. 이 표준은
그 내용을 다시 쓰지 않는다 — [스킬 제작 방법 0절](authoring.md#0-먼저--스킬-만드는-법은-공식이-가르친다).

## 6. 남의 환경에서 돌아가야 한다

**플러그인은 자기 디렉토리 안에서 완결된다.** 설치되는 것은 그 디렉토리뿐이고, 받는 쪽
환경에는 만든 사람의 홈 디렉토리도 사내 서버 접근도 없다.

```
  내 환경에서만 되는 것 — 올리기 전에 걷어낸다
  ─────────────────────────────────────────────────────────────
  /Users/<나>/... · ~/Documents/...     남의 홈에는 없다
  사설 IP · 내부 호스트 이름             접근 권한이 없다
  ../ 로 플러그인 밖을 가리키는 경로      설치본에는 그 밖이 없다
  내가 깔아둔 다른 플러그인의 스킬        남은 안 깔았다
```

자기 파일을 부를 때는 **설치 위치를 가리키는 변수**를 쓴다. 플러그인이 어디에 풀릴지는
설치하는 쪽이 정한다.

### 걷어낼 수 없으면 선언한다

외부 도구·접근 권한·다른 플러그인이 **정말 필요하면** 지우지 않아도 된다. 대신
`README.md` 의 「전제 조건」에 적어 **설치하는 사람이 미리 알게 한다.**

## 7. `README.md`

쓰는 사람이 **설치할지 말지 결정할 수 있을 만큼** 쓴다.

```markdown
# <이름>

한 줄 설명.

## 무엇을 하는가
어떤 상황에서 무엇을 해주는지. 결과가 어떻게 나오는지.

## 쓰는 법
호출 예시. `/<플러그인>:<스킬>` 또는 어떤 말을 하면 뜨는지.

## 전제 조건
| | |
|---|---|
| 외부 도구 | `jq` · `docker` … / 없음 |
| 접근 권한 | 사내 DB · 특정 레포 … / 없음 |
| 다른 플러그인 | `foo@terroir-community-plugin` … / 없음 |

## 아는 한계
할 수 없는 것 · 주의할 것.

## 소유자
<이름> (@<GitHub 핸들>)
```

**「전제 조건」과 「아는 한계」를 비우지 않는다.** 품질 심사가 없는 마켓이라, 만든 사람이
적는 것이 유일한 안전장치다.

**없으면 「없음」이라고 적는다.** 빈칸으로 두지 않는다 — 안 적은 것과 확인하고 없는 것은
읽는 쪽에서 구별되지 않는다. 셋 다 「없음」이면 어디서든 그대로 돌아간다는 뜻이고, 그게
가장 좋은 상태다.

**CI 는 이 절들을 검사하지 않는다.** 「없음」 한 줄로 통과하는 검사는 키 입력만 늘리고
정보를 만들지 않는다 — 확인하고 없는 것과 통과하려고 적은 것이 같은 문자열이 된다.
본인이 머지하는 마켓이라 그 차이를 볼 사람도 없다. 그래서 강제하지 않고 **설치하는
사람이 보고 고른다**는 사실에 맡긴다.

## 8. 올린 뒤

| | |
|---|---|
| 머지 | 자기 플러그인은 CI 통과 후 **본인이 머지한다.** 남의 것은 그 소유자 승인이 필요하다 |
| 고칠 때 | `version` 을 올린다. 올리지 않으면 CI 가 **경고**한다 — 막지는 않는다 |
| 그 외 | 내리기 · 이관 · 남의 것 고치기는 [마켓을 바꾸는 절차](operations.md) |

## 9. CI 가 보는 것

| 검사 | |
|---|---|
| 분류 | `plugins/` 바로 아래가 허용 목록 안인가 · 그 아래가 정확히 1단계인가 |
| 이름 | 문자 규칙 · 마켓 전체에서 유일한가 · 디렉토리명 == `name` |
| 매니페스트 | `description` · `version` · `author` · `metadata.owner` 가 있는가 · 길이 상한 |
| 파일 | `README.md` 가 있는가 · `SKILL.md` 가 최소 하나 있는가 |
| 스킬 | frontmatter 의 `name` · `description` 존재 · `description` 길이 |
| 버전 | 파일이 바뀌었는데 `version` 이 그대로인가 — **경고만 한다.** 올리지 않는 것이 의도일 수 있다 |
| 목록 | `marketplace.json` 의 각 줄이 실제 디렉토리를 가리키나 · 빠진 플러그인은 없나 · 헤더가 정본과 같은가 |
| 소유 | 플러그인마다 `CODEOWNERS` 줄이 있나 · 그 소유자가 `metadata.owner` 와 같은가 |
| 스키마 | `claude plugin validate` 통과 |

**떨어지면 메시지가 고치는 법을 알려준다.** 알려주지 않으면 그건 CI 의 버그다.
