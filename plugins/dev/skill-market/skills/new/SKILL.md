# 마켓에 올리기

사용자가 만든 스킬을 `VntgCorp/terroir-community-plugin` 에 올린다.

**이 스킬은 마켓 규약만 안다.** `SKILL.md` 본문을 어떻게 잘 쓰는지는 공식
`skill-creator` 가 가르치고 그쪽이 정본이다. 내용 작업이 필요하면 그쪽으로 넘긴다.

**규약의 정본은 레포의 `docs/standard.md`(무엇이 규칙인가) 와 `docs/authoring.md`(절차) 다.** 아래 절차는 그 문서가 시키는 일을
순서대로 하는 것이고, 규칙 값이 어긋나면 **문서가 이긴다.** 절차 중에 문서를 읽는다.

---

## 1. 레포를 확보한다

현재 디렉토리가 `terroir-community-plugin` 인지 본다. 아니면 클론한다.

```bash
git clone https://github.com/VntgCorp/terroir-community-plugin
cd terroir-community-plugin
```

이미 있으면 `git checkout main && git pull` 로 최신으로 맞춘다. **낡은 상태에서
이름 중복을 검사하면 틀린 답이 나온다.**

`docs/standard.md` 와 `docs/authoring.md` 를 읽는다. 이후 판단은 그 문서를 근거로 한다.

## 2. 무엇을 만드는지 듣는다

이미 만든 스킬이 있는지, 아니면 지금부터 만드는지 가른다.

| 상황 | |
|---|---|
| 이미 `SKILL.md` 가 있다 | 그 파일을 가져다 3절로 간다 |
| 아직 없다 | 무엇을 하는 스킬인지 듣는다. 본문 작성은 공식 `skill-creator` 가 낫다고 알린다 |

## 3. 분류를 정한다

**한 줄로 판정한다 — 이 스킬이 소스코드나 인프라를 건드리나?**

- 예 → `dev`
- 아니오 → `work`

「누가 쓰는가」가 아니라 **「무엇을 건드리는가」**다. 개발자가 쓰는 회의록 정리 스킬은
`work` 다. 애매하면 `work` 로 간다. 사용자에게 판정 근거를 한 줄로 말하고 확인받는다.

허용 분류는 `.github/categories.txt` 가 정본이다. 그 파일을 읽어 확인한다.

## 4. 이름을 정한다

규칙은 `docs/standard.md` 3절이 정본이다. 정하기 전에 **중복을 실제로 조회한다.**

```bash
node -e "console.log(JSON.parse(require('fs').readFileSync('.claude-plugin/marketplace.json')).plugins.map(p=>p.name).join('\n'))"
```

### 겹치지 않으면

그 이름으로 간다.

### 겹치면 — 사용자에게 알리고 고르게 한다

**마음대로 이름을 바꿔서 진행하지 않는다.** 아래를 그대로 알린다.

```
  '<이름>' 은 이미 있습니다.  (소유자 @<metadata.owner>, <분류>)
  무엇을 하는 것인지: <그 플러그인의 description>

  이름은 마켓 전체에서 유일해야 해서, 올리려면 다른 이름이 필요합니다.
```

그리고 **둘을 묻는다.**

| 물을 것 | 왜 |
|---|---|
| 같은 일을 하는 것인가 | 그렇다면 이미 있는 것을 쓰거나 그쪽에 기여하는 편이 나을 수 있다. 비슷한 스킬이 둘이면 설치하는 사람이 매번 고민한다 |
| 다른 일이라면 어떤 이름으로 할까 | 쓰임을 좁히는 말을 2~3개 제안하고 고르게 한다 — `<이름>-fe` · `<이름>-sales` 처럼 |

제안할 때 **왜 그 모양인지도 한 줄로 말한다** — 숫자(`-2`)는 설치하는 사람이 둘 중
무엇을 고를지 알 수 없어 쓰지 않고, 소유자 접두어도 쓰지 않는다.

**남의 플러그인을 지우거나 이름을 바꾸는 것은 선택지로 제시하지 않는다.** 구조상
막혀 있지 않지만 쓰던 사람의 설치가 끊긴다.

사용자가 고른 이름으로만 다음 절로 간다.

## 5. 뼈대를 만든다

```
plugins/<분류>/<이름>/
├── .claude-plugin/plugin.json
├── README.md
└── skills/<이름>/SKILL.md
```

각 파일의 필수 필드와 양식은 `docs/standard.md` 2·4·5·7절이 정본이다. 그대로 채운다.

채우면서 **사용자에게 물어야만 아는 것**이 둘 있다.

| | |
|---|---|
| `author.name` | 화면에 뜨는 사람 이름 |
| `metadata.owner` | **GitHub 핸들.** 사람 이름이 아니다. 모르면 `gh api user --jq .login` 로 확인시킨다 |

### 남의 환경에서 돌아가는지 묻는다 — 건너뛰지 않는다

올린 사람 환경에서만 되는 플러그인은 설치는 되고 **실행이 안 된다.** 뼈대를 채우기 전에
아래 셋을 묻고, 답을 `README.md` 의 「전제 조건」에 그대로 넣는다.

```
  ① 이 스킬이 쓰는 외부 도구가 있습니까?
       jq · docker · python 처럼 Claude Code 밖의 명령

  ② 특정 접근 권한이 필요합니까?
       사내 DB · 특정 레포 · VPN · 사내망

  ③ 다른 플러그인이 깔려 있어야 합니까?
```

**셋 다 「없음」이면 그렇게 적는다.** 빈칸으로 두지 않는다 — 안 적은 것과 확인하고 없는
것은 읽는 쪽에서 구별되지 않는다.

CI 는 이 절을 검사하지 않는다. **그래서 여기서 묻는 것이 유일한 자리다** — 넘기면
아무도 묻지 않는다.

그리고 초안을 **읽어서 아래를 찾는다.** 있으면 사용자에게 알리고 고치거나 선언하게 한다.

| 찾을 것 | 왜 |
|---|---|
| `/Users/...` · `~/...` 같은 절대 경로 | 남의 홈에는 그 경로가 없다 |
| 사설 IP · 내부 호스트 이름 | 받는 쪽에 접근 권한이 없다 |
| `../` 로 플러그인 밖을 가리키는 경로 | 설치본에는 그 밖이 없다 |
| 다른 플러그인의 스킬 호출 | 남은 그것을 깔지 않았다 |

자기 파일을 부를 때는 **설치 위치를 가리키는 변수**를 쓰게 한다. 플러그인이 어디에
풀릴지는 설치하는 쪽이 정한다.

### 「아는 한계」도 비우지 않는다

품질 심사가 없는 마켓이라, 무엇을 할 수 없는지를 만든 사람이 적는 것이 유일한
안전장치다. 사용자가 안 적으면 물어서 받는다.

## 6. 목록에 더하고 검사한다

**`.claude-plugin/marketplace.json` 의 목록에 한 줄을 더한다.** Claude Code 는 그 목록만
읽으므로, 디렉토리를 만들어도 목록에 없으면 아무도 설치할 수 없다.

```json
  { "name": "<이름>", "source": "./plugins/<분류>/<이름>", "category": "<분류>" }
```

조립기로 대신 적어도 된다. 정렬·들여쓰기는 검사하지 않으니 어느 쪽이든 통과한다.

```bash
node .github/scripts/assemble-marketplace.mjs            # 목록을 대신 적어준다 (선택)
node .github/scripts/check-structure.mjs
node .github/scripts/check-marketplace.mjs
node .github/scripts/check-version-bump.mjs origin/main   # 고치는 경우에만 걸린다
claude plugin validate .
```

**이미 있는 플러그인을 고쳤다면 `version` 을 올린다** — 올리지 않으면 CI 가 경고를 띄운다(막지는 않는다).
무엇을 올릴지는 `docs/versioning.md`, 두 번째 버전부터는 `CHANGELOG.md` 도 쓴다.

검사가 떨어지면 **메시지가 고치는 법을 알려준다.** 그대로 고치고 다시 돌린다.
메시지가 고치는 법을 안 알려주면 그건 CI 의 버그다 — 사용자에게 이슈를 권한다.

## 7. 올린다

```bash
git checkout -b feat/<이름>
git add plugins/<분류>/<이름> .claude-plugin/marketplace.json
git commit -m "feat(<분류>): <이름> 추가"
gh pr create
```

PR 본문에 **무엇을 하는 스킬인지와 아는 한계**를 적는다.

올린 뒤 알린다 — **CI 가 통과하면 본인이 머지한다. 누구의 승인도 기다리지 않는다.**
단 뼈대(`docs/` · `README.md` · `CLAUDE.md` · `.github/`)를 건드렸다면 플랫폼개발팀 승인이 필요하다.

## 올리는 것이 아니면

이 스킬은 **새로 올리는 경로만** 안다. 사용자가 다른 일을 원하면 `docs/operations.md`
를 읽고 그 절차를 따른다 — 그 문서가 정본이다.

| 사용자가 원하는 것 | |
|---|---|
| 올린 것 고치기 · 버전 올리기 | `docs/versioning.md` 로 기준을 보고 `operations.md` A1 |
| 남의 플러그인 고치기 | `operations.md` A2 — 소유자를 리뷰어로 지정하는 관례가 있다 |
| 내리기 | `operations.md` A3 — **소유자 동의를 먼저 확인한다** |
| 소유자 이관 | `operations.md` A4 — 양쪽 동의가 필요하다 |
| 분류 추가 · 마켓 이름 변경 | `operations.md` B1·B2 — 팀 승인이 필요하다고 알린다 |

## 하지 않는 것

- **`SKILL.md` 본문을 대신 써주지 않는다.** 무엇을 하는 스킬인지는 사용자가 안다.
  초안이 필요하면 공식 `skill-creator` 로 넘긴다
- **사용자 대신 머지하지 않는다.** PR 생성까지가 이 스킬의 끝이다
- **규칙 값을 외워서 말하지 않는다.** 길이 상한·이름 규칙 같은 것은 `docs/standard.md`
  를 읽어서 답한다. 외워 두면 문서가 바뀔 때 갈린다
