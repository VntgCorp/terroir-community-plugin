# 보안 점검

**작성된 코드를 사내 보안 기준에 비추어 점검한다.** 대상은 이미 요구사항에 맞게 돌아가는 사내 시스템이다.

```
/vsecu-review          점검만 한다
/vsecu-review --fix    점검하고, 리포트를 낸 뒤에 고친다
```

- **점검을 요청받았다면** → 아래 **「점검 절차」를 그대로 따른다**
- **특정 영역의 판단만 필요하면** → **「영역별 상세 기준」** 에서 해당 절만 찾아 읽는다

아래 **1장의 함정 번호를 `1-N` 으로 참조한다. 1장 전 항목이 점검의 1차 기준이다.**
(항목 수는 고정하지 않는다 — 표가 늘어날 때마다 이 숫자를 따로 맞추면 어긋난다. 실제로 두 번 어긋난 적이 있다.)
**문서의 마지막 항목 번호까지 빠짐없이 돈다.** 개수가 기억과 다르면 **문서를 다시 열어 확인한다** — 문서가 틀렸다고 단정하고 넘기지 않는다. 실제로 24개 중 21개만 돌고 나머지를 「기준 문서 불일치」로 적은 리포트가 있었다.

## 적용 원칙

1. **언어·프레임워크와 무관하게 적용한다.** 아래 항목은 *"무엇을 보장해야 하는가"* 이고, 구현은 **그 언어·프레임워크의 표준 안전 기제**로 한다. 예시 언어가 다르다고 예외가 되지 않는다.
2. **이미 검증된 기제가 있는 문제를 직접 구현하지 않는다.** 이스케이프·HTML 정화, 암호·해시·서명·토큰, 세션 관리, 파서(마크다운·CSV·XML)를 손으로 만들지 않는다.
   **"의존성을 늘리고 싶지 않아서"는 사유가 되지 않는다.** 의존성 추가가 곤란한 사정이 있다면 그것부터 확인한다. **코드베이스에 이미 손으로 만든 것이 있어도 그것을 선례로 삼지 않는다** — 그 옆에 하나를 더 만드는 순간 그것이 이 저장소의 규범이 된다.
3. **차단 목록이 아니라 허용 목록으로 판단한다.** "위험한 것을 지운다"가 아니라 "허용할 것만 통과시킨다".
4. **기준과 기능 요구사항이 충돌해 보이면** 기능을 포기하지도 기준을 어기지도 말고 **안전한 구현 경로**를 찾는다. 그것도 없으면 임의로 정하지 말고 **사용자에게 확인을 받는다.**
   **위험을 주석에 적고 그대로 출고하는 것은 확인이 아니다.** "노출 전에 인증을 붙이는 것을 고려하라" 같은 문장을 코드에 남겼다면, 확정되지 않은 경계를 발견했다는 뜻이다. 적지 말고 물어라.
5. **확인한 것과 확인하지 않은 것을 구분한다.** 검증하지 않은 항목을 "문제없음"으로 넘기지 않는다.
   **코드의 주석은 증거가 아니다** — "검증됨", "안전함", "이 규모에서는 문제없음"은 주장이지 확인이 아니고, **이 세션이 직접 쓴 주석도 마찬가지다.** 판단하지 못한 것은 판단하지 못했다고 밝힌다.

## 0장. 코드만으로 정할 수 없는 것

**보안 경계를 추측으로 정하지 않는다.**

점검 대상은 이미 돌아가는 시스템이다. **코드에서 읽히는 것은 묻지 말고 읽는다** — 로그인 방식, 인가 구현, 허용 출처 목록, 데이터 스키마는 코드가 답이다.

**사람만 아는 것만 묻는다.** 아래가 확정되지 않으면 임의로 고르지 말고 「확인 불가」로 올린다.

> **괄호 안이 실제로 물을 문장이다. 그대로 묻는다.** 괄호 밖은 판정에 쓸 근거와 선택지이고 **질문에 섞지 않는다.**
> 프록시·로드밸런서·종단·평문 HTTP 같은 말을 붙이면 "잘 모르겠는데요"가 돌아오고, 그러면 묻지 않은 것과 같아진다.
> **상대가 개발자여도 마찬가지다** — 앱을 만든 사람이라고 인프라 구성을 아는 것은 아니다.
> 답을 못 받으면 용어를 더 쉽게 바꿔 다시 묻는다. **질문을 빼지 않는다.**

- **이 리소스를 누가 볼 수 있어야 하는가** (로그인 안 한 사람도 볼 수 있어야 합니까? 로그인했으면 누구나 됩니까, 아니면 **올린 사람만** 봐야 합니까?) — 전체 공개 / 인증된 사용자 전원 / 소유자만 / 특정 역할
  **시스템이 실제로 가를 수 있는 선으로 묻는다.** 부서·직급처럼 그 앱이 알지 못하는 기준으로 물으면 답을 받아도 구현할 수 없다
- 이 데이터가 어느 등급인가 (이름·연락처·주민번호·계좌번호·건강정보가 들어갑니까?) — 개인정보·결제정보·인증정보가 포함되는가
- **사용자가 접속하는 주소가 `https://` 인가** (브라우저 주소창에 **자물쇠**가 보입니까? 주소가 **https** 로 시작합니까?) — 앱이 평문 HTTP만 듣고 있어도 앞단에서 암호화를 끝내면 정상이다. **확인되지 않으면 넘겨짚지 않는다**
- **이 산출물은 어떻게 배포·공유되며 누가 열 수 있는가** (링크를 받은 사람은 누구나 열어도 됩니까?) — 접근 범위가 코드가 아니라 배포 설정에 있는 경우가 있다 (**1-24**)

넓은 쪽을 고르면 취약점이 되고 좁은 쪽을 고르면 기능이 깨진다. **한 줄 질문이 양쪽을 막는다.**

**질문은 이 넷뿐이다.** 로그인 방식, 인가 구현, 허용 출처 목록은 **코드를 읽으면 나오므로 묻지 않는다.**
상대가 답할 수 없는 말로 물으면 "잘 모르겠는데요"가 돌아오고, 그것은 묻지 않은 것과 같다.
**용어를 바꿔서 다시 묻는다. 질문을 빼지 않는다.**

## 1장. 특히 놓치는 것

적용 원칙에서 유도되지 않는다. 각각 별도의 사실이므로 개별 확인한다.

| # | 사실 |
|---|---|
| **1** | **시크릿에 fallback 기본값을 두지 않는다.** 값이 없으면 **기동 시점에 실패**시킨다. 기본값이 있으면 운영에서 설정을 누락해도 정상 기동하고, 그 순간부터 누구나 아는 값을 쓴다. "개발용", "로컬 전용" 주석은 방어가 아니다 |
| **2** | **조회에도 인가를 건다.** 생성·수정에는 소유자 검사를 넣고 조회·다운로드·페이지 렌더에 빠뜨리는 비대칭이 가장 흔하다. 리소스에 공개/비공개 필드가 있으면 그 ID를 받는 **모든** 엔드포인트를 열거해 확인한다 |
| **3** | **상한 검사는 자원을 쓰기 전에 한다.** 전부 읽고 전부 파싱한 뒤 행 수를 세면 이미 늦다. **요청 본문 전반(JSON·폼 파싱 포함)**, 업로드, 역직렬화, 압축 해제는 모두 **읽는 중 누적 검사**한다. 프레임워크의 요청 크기 상한은 원본 바이트만 막을 뿐, 파싱 후 객체가 몇 배로 부푸는 것은 막지 못한다. **`Content-Length` 헤더값만 보고 검사했다고 여기지 않는다** — 그 헤더를 생략하는 청크 전송(`Transfer-Encoding: chunked`)은 헤더 검사를 통째로 건너뛴다. 헤더가 있든 없든 실제로 읽은 바이트 수를 누적해서 상한을 넘으면 그 자리에서 끊는다 |
| **4** | **상한을 통과한 값도 곱하면 넘친다.** `offset = page * size` 는 두 값을 각각 검사해도 곱에서 넘쳐 음수가 된다. 넓은 타입으로 계산하거나 곱한 **결과**에 상한을 건다 |
| **5** | **외부 입력에 비례해 커지는 저장소는 상한이 없다** — 캐시·원장·로그·세션 맵이 모두 해당한다. 검색어·경로·식별자를 키나 항목으로 쓴다면 **크기 상한과 만료**가 필수다. 담기는 값에 자격증명·개인정보가 섞여 있지 않은지, **그것을 매번 전부 읽는 코드가 없는지**도 함께 확인한다 |
| **6** | **개별 연산이 원자적이어도 전체가 원자적이지는 않다.** 조건부 갱신을 이어 붙이고 실패 시 수동 보상(환불·롤백)을 넣는 구조는 **보상 코드가 실행될 때까지 프로세스가 살아 있어야** 성립한다. 차감과 지급, 예약과 확정은 트랜잭션으로 묶는다 |
| **7** | **난수를 잘라 쓰지 않는다.** UUID 앞 8자는 32비트다. 접근을 통제하는 값은 **128비트 이상**, 추측을 막아야 하는 값(쿠폰·초대·조회 코드)은 64비트 이상 |
| **8** | **경로 결합 함수는 절대경로를 받으면 기준 디렉터리를 무시**하는 언어가 있다. 결합 후 이탈 검사 |
| **9** | `resolve()`·`Clean()`·`normalize()` 는 **렉시컬**이라 심볼릭 링크를 따라가지 않는다. **`realpath` 를 먼저** 호출한 뒤 비교하고, **문자열 접두사 비교를 쓰지 않는다**(`/app/data` 기준에서 `/app/data-evil` 통과) |
| **10** | **인자 배열도 안전하지 않다.** 셸이 없어도 `-` 로 시작하는 값은 플래그로 파싱된다(ripgrep `--pre=`, git `--upload-pack=`, tar `--checkpoint-action=exec=`, rsync `-e`, ssh `-oProxyCommand=`). 인자 앞 `--` 삽입 또는 `-` 시작값 거부 |
| **11** | **환경변수도 실행 경로다.** argv가 고정이어도 신뢰 못 할 값을 `env` 에 병합하면 코드 실행이다(`LD_PRELOAD`, `NODE_OPTIONS`, `PYTHONSTARTUP`, `BASH_ENV`, `GIT_SSH_COMMAND`). 허용 목록으로 환경을 구성한다 |
| **12** | **URL·출처 비교는 파서로 정규화한 뒤 호스트만** 한다. `netloc` 에는 `user:pass@` 가 포함되어 `https://trusted.com@evil.com` 이 통과하고, `endswith("trusted.com")` 은 `eviltrusted.com` 을, `startswith` 는 `trusted.com.evil.com` 을 통과시킨다 |
| **13** | **CORS 와일드카드에 "브라우저가 막아주겠지"로 기대지 않는다.** 자격증명 허용 설정에서 프레임워크가 와일드카드를 **출처 반사**로 바꾸는 경우가 있다 |
| **14** | 허용 목록을 통과해도 **리다이렉트가 SSRF를 되살린다.** 대부분의 클라이언트가 3xx를 자동 추적한다. 수동 처리 + 매 홉 재검증 |
| **15** | **업로드 파일의 타입은 확장자나 클라이언트가 보낸 Content-Type이 아니라 실제 내용(매직바이트)으로 판정한다.** 헤더값은 요청자가 임의로 지정 가능하다. HTML·SVG·스크립트는 이미지로도 허용하지 않는다 — 다른 사용자가 그 파일을 열람하는 순간 저장형 XSS가 된다 |
| **16** | **발급한 세션·토큰에는 무효화 수단을 갖춘다.** 로그인을 SSO에 위임해도 그 이후 앱이 자체로 발급하는 세션·토큰은 앱의 책임이다. 로그아웃·권한 변경·계정 정지·비밀번호 변경이 앱에 즉시 반영되지 않으면, 회수돼야 할 접근이 만료 전까지 계속 유효하다 |
| **17** | **개발용 시드 데이터·샘플 계정은 파일 이름 자체를 프레임워크의 기본 관례에서 벗어나게 한다.** 설정값 하나를 지우는 것만으로는 안 막힌다 — 프레임워크가 관례적 파일명(`data.sql`, `seeds.rb` 등)을 기본으로 다시 찾아 실행한다. 운영에서 실행될 조건(프로파일·환경변수)이 명시적으로 켜져야만 로드되게 한다 |
| **18** | **클라이언트가 잘못 보낸 요청(깨진 본문, 지원 안 하는 형식, 타입 불일치)은 4xx로 분류한다.** catch-all 예외 처리만 두면 이런 것도 500과 함께 서버 오류 로그로 잡혀, 인증 없이도 로그를 부풀릴 수 있다 |
| **19** | **요청 파이프라인 앞단(필터·미들웨어)에서 오류를 직접 응답해야 한다면, 프레임워크의 표준 오류 라우팅(에러 페이지 전달·재진입)을 우회할지부터 확인한다.** 표준 경로를 타면 그 오류 응답이 인증·인가 같은 뒷단 컴포넌트를 다시 통과하면서 상태(상태 코드 등)가 뒤바뀔 수 있다 |
| **20** | **자체 로그인(아이디·비밀번호를 직접 검증하는 로그인)을 구현한다면 반복 시도에 지연·잠금을 건다.** 계정 축에는 지연·추가 확인을 걸고, **잠금은 어느 축에서도 기본값이 아니다** — 계정 축 잠금은 남의 계정을 잠그는 수단이 되고, 출처 축 잠금은 공유 IP 뒤의 전원을 막는다(**1-23**). 로그인을 SSO에 위임한다면 해당 없음 |
| **21** | **자체 로그인을 구현한다면 계정 존재 여부와 무관하게 처리 시간을 맞춘다.** 계정이 없을 때도 더미 해시로 비교 연산을 수행해, 응답 시간만으로 계정 존재 여부가 드러나지 않게 한다. 로그인을 SSO에 위임한다면 해당 없음 |
| **22** | **인증·인가 실패, 권한 변경 같은 보안 사건은 추적 가능하게 기록한다.** 로그인 시도·실패, 권한 변경, 계정 정지 같은 이벤트를 남기지 않으면 사고 발생 후 무슨 일이 있었는지 재구성할 수 없다. 기능 하나만 볼 때는 "어디에 남길지" 설계할 계기 자체가 없어, 앱 전체가 완성된 뒤에야 빠진 게 보인다 |
| **23** | **방어 조치 자체가 남용되거나 자해가 될 수 있는지 본다.** 행위 목록으로 외우지 말고 **성질로 판별한다** — ⑴ **상대가 유발시킬 수 있는가**(잠금·차단·삭제·알림·정지), ⑵ **사람 없이 자동으로·정기적으로 실행되는가**(스케줄 작업, 자동 복구·자동 격리·자동 되돌리기). 둘 중 하나라도 해당하면 **잘못 발동했을 때 무엇이 멈추는지**를 먼저 적고, 그 대가가 큰 쪽은 **자동 조치 대신 통보만** 한다. 무인 실행은 실패해도 아무도 모른다.<br>**잠금은 어느 축에서도 기본값이 아니다.** 계정 축에는 지연·추가 확인만 건다(계정 축 잠금은 남의 계정을 잠그는 수단이 된다). 출처 축도 지연·추가 확인이 기본이고, **그 출처가 한 사람만 가리킨다고 확인된 경우에만** 잠금을 쓴다 — 사내망·모바일 캐리어·VPN·클라우드 NAT 뒤에서는 하나의 출처를 다수가 공유하므로, 출처 축 잠금이 전원 차단이 된다. 출처 값 자체도 **앞단 프록시가 덮어쓴다고 확인된 경우에만** 믿는다(`X-Forwarded-For` 등) |
| **24** | **접근 통제가 코드 밖에 있는 산출물이 있다.** 스크립트 웹앱·공유 문서·자동화 플로우(Apps Script·스프레드시트·Power Automate·VBA)는 인증이 애초에 코드에 없고 **배포·공유 설정에 있다.** "안 열려요"를 가장 빠르게 없애는 방법이 범위를 넓히는 것이라, 설정은 **넓은 쪽으로 수렴한다**(3장 9번과 같은 이유). **공유 링크는 인가가 아니다** — 주소를 아는 사람 전원이 접근하고, 회수해도 이미 퍼진 링크는 막지 못한다. **확인 대상은 "외부 전체 공개"만이 아니다** — 「사내 도메인 전원」, 「링크를 아는 조직 구성원」도 넓은 설정이다. 부서·팀 단위로 정한 범위라면 **조직 전체 공개는 그 자체로 위반**이다. 조직 안이라는 이유로 통과시키지 않는다. 자격증명은 스크립트 본문·시트 셀이 아니라 **플랫폼의 비밀 저장소**에 둔다. **코드가 그 설정에 의존한다면 그 사실을 코드 쪽에서 확인하거나, 설정에 의존하지 않는 경로로 바꾼다** — 설정이 나중에 바뀌어도 코드는 알지 못한다. 코드만 봐서는 판정할 수 없으므로 **0장에서 반드시 묻는다** |

# 점검 절차

**점검 모드로 호출됐다면 이 절차를 그대로 따른다.**

## 대상 결정

경로가 주어지면 그것. 아니면 **이 세션에서 작성·수정한 파일 전부**. 그것도 없으면 대상을 묻는다. 임의로 폴더 전체를 훑지 않는다.

**대상 파일 목록을 먼저 만들고 그 목록을 근거로 삼는다.** 특히 다른 세션·다른 사람이 만든 코드를 점검할 때는 무엇을 봐야 하는지가 기억에 없으므로, 목록 없이 시작하면 **파일이 통째로 빠진 채 "준수"가 나온다.** 목록의 각 파일이 어떤 항목에 걸리는지 확인했고, 읽지 않은 파일은 ③에 그대로 적는다.

대상이 많으면(30개 파일 초과 등) **전부 훑었다고 하지 말고**, 우선순위를 정해 점검한 범위를 밝힌다.

## 가능하면 실행해서 확인한다

**정적 판독은 "없는 것"을 놓친다.** 서버·CLI 가 뜨는 상태라면 실제 요청·입력을 던져 판정한다 — 큰 본문, 경계값, 잘못된 토큰, 권한 없는 계정, 경로 우회 시도. 읽기만 해서는 "상한이 있네"에서 멈추기 쉽고, 그 상한이 **어느 경로에만** 걸려 있는지는 던져봐야 드러난다.

실측한 항목은 요약표에 그렇게 표시하고, 실행하지 못했으면 ③에 적는다. **읽어서 내린 판정과 던져서 확인한 판정은 신뢰도가 다르다.**

방어가 동작하더라도 **그 이유가 내 코드인지 확인한다.** 프레임워크·컨테이너·라이브러리의 기본 동작이 막아준 것이라면 지금은 안전해도 구성이 바뀌면 무너진다 — 위반은 아니지만 하드닝 항목으로 남긴다.

## 항목을 순회한다

**코드를 읽고 눈에 띄는 문제를 고르는 방식으로 하지 않는다.** **1장** 전 항목은 대부분 **"없는 것"을 찾는 문제**(인가 없음, 트랜잭션 없음, 상한 없음)이고, 없는 것은 읽으면서 눈에 띄지 않는다.

항목마다 다음 순서로 한다.

1. 이 코드에서 그 항목이 걸리는 **지점을 먼저 열거**한다 — 예: 1-2 라면 리소스를 반환·수정하는 엔드포인트 전부
2. 열거한 지점을 하나씩 판정한다
3. 상태를 기록한다

**순서**: **1장** 전 항목 → 0장(확정되지 않은 경계가 남았는가) → 변경된 영역에 해당하는 아래 15개 장.

## 판정은 넷 중 하나

| 상태 | 뜻 | 반드시 함께 적을 것 |
|---|---|---|
| **위반** | 문제 발견 | **위험도** — `파일:줄` — 무엇이 위험한가 — 어떻게 바꿀 것인가 |
| **준수** | 지점이 있고 올바르게 처리됨 | 확인한 `파일:줄` |
| **해당 없음** | 그 항목이 걸릴 지점이 없음 | **왜 없는지 근거** |
| **확인 불가** | 코드만으로 판단 못 함 | 사용자에게 물을 질문 |

**"해당 없음"에 근거를 반드시 적는다.** 근거를 쓰려면 실제로 찾아봐야 하고, 안 찾았으면 못 쓴다. 이 칸이 비면 점검하지 않은 것과 구분되지 않는다 — **"위반 없음"과 "확인하지 않음"은 전혀 다른 결과인데 겉보기가 같다.**

**확인 불가는 위반이 아니라 질문이다.** 리소스의 공개 범위, 허용 출처, 데이터 등급처럼 요구사항이 정해야 할 것은 추측해서 판정하지 말고 **0장**의 질문으로 올린다.

**적어놓고 끝내지 말고 묻는다.** 사람이 답할 수 있는 자리면 ③ 을 낸 뒤 ④ 앞에서 **모아서 한 번에 묻는다.** 리포트에만 적어두면 아무도 돌아와서 답하지 않고, 그 경계는 영영 미확정으로 남는다.

| 상황 | 한다 |
|---|---|
| 답을 받았다 | 그 항목을 **다시 판정**하고, 근거에 `점검 중 확인 (날짜)` 를 적는다 |
| 답을 못 받았다 | **확인 불가로 남긴다.** 건수를 ④ 에 적는다 |
| 사람이 없다 (CI·배치) | 묻지 않고 확인 불가로 남긴다. 점검이 멈추지 않게 한다 |

**답을 재촉해서 받아낸 값으로 판정하지 않는다.** 프롬프트를 치우려고 아무 값이나 고르면 「확인 불가」보다 나쁜 **거짓 준수**가 된다. 확인 불가는 정직한 공백이지만 거짓 준수는 통과 도장이 찍힌 구멍이다.

**답의 출처를 반드시 남긴다.** `요구사항 문서 2-1 표` 와 `점검 중 개발자 구두 확인` 은 무게가 다르다. 나중에 그 판단이 틀린 것으로 드러났을 때 어디서 온 값인지 알 수 있어야 한다.

**질문이 이 자리에서 나왔다는 것 자체가 신호다.** **코드에서 읽히는 것을 질문으로 올리지 않는다.** 0장은 사람만 아는 것만 묻는 자리다.

**방어가 있는 것과 방어가 도는 것은 다르다.** 허용 목록·검증 메서드·더미 해시·인가 함수가
코드에 **있다는 것만으로 준수가 아니다.** 준수로 적기 전에 셋을 확인한다.

| | 놓치는 형태 |
|---|---|
| **호출되는가** | 정의만 되어 있고 아무도 부르지 않는 메서드는 방어가 아니다 |
| **내용이 맞는가** | 허용 목록 안에 위험한 값이 들어 있지 않은가 |
| **모든 경로에 걸리는가** | 한 핸들러에만 걸려 있고 형제 핸들러는 비어 있지 않은가 |

**준수의 근거에는 그 방어를 「쓰는」 지점을 적는다.** 방어가 정의된 위치만 적은 준수는 근거가 아니다.
`dummyHash` 필드가 있다가 아니라 `로그인 실패 경로에서 dummyHash 로 비교한다`여야 한다.

실제로 이 형태로 네 건을 한꺼번에 놓친 점검이 있었다 — 허용 목록이 있어서 준수(목록 안에
`text/html` 이 있었다), 더미 해시가 있어서 준수(만들어 두고 쓰지 않았다), 인가 함수가 있어서
준수(빈 역할이면 통과했고, 소유자 검사는 정의만 되어 호출되지 않았다).

**주석을 근거로 삼지 않는다**(**적용 원칙 5**). 특히 그 주석을 이 세션이 직접 썼다면 더욱 그렇다.

## 위반에는 위험도를 붙인다

**위험도는 판단하지 않는다. 아래 표에서 읽는다.** 같은 코드가 세션마다 다른 등급을 받으면
통과 판정이 흔들린다. 실제로 지난 리포트 6건에서 표기가 네 가지로 갈렸다 — 그래서 표로 고정한다.

| 등급 | 뜻 | 처리 |
|---|---|---|
| **상** | 이 결함 하나만으로 경계가 넘어간다 — 남의 자격·권한을 얻는다, 남의 데이터를 읽거나 바꾼다, 서버에서 코드가 돈다 | 고친다. 고친 뒤 **새 세션에서 재점검**한다. **통과 대상이 아니다** |
| **중** | 뚫리지는 않는다. 그러나 **사고가 진행 중일 때 멈출 수단이 없다.** 또는 다른 조건이 하나 더 맞아야 악용된다 | **플랫폼정보보호팀과 상의**한다. 상의 결과 위험도가 낮다고 판단되면 통과 |
| **하** | 지금 구성에서 악용 경로가 없다. 사후 파악·위생·견고성 문제이거나, 구성이 바뀌면 문제가 될 수 있다 | 통과 |

**중과 하를 가르는 선** — 피해가 더 커지는 것을 막는 수단이면 **중**(봉쇄).
이미 벌어진 일을 나중에 알아내는 수단이면 **하**(기록).

**하드닝은 등급 밖이다.** 위반이 아니므로 등급을 매기지 않고 기록만 한다.

**지금은 다른 수단이 막고 있지만 그 수단이 사라지면 뚫리는 것도 하드닝이다.** 기준에 적힌 방어는 없는데 무관한 제약이 우연히 막고 있는 경우가 그렇다 — 악용 경로가 지금 없으므로 위반은 아니고, 무엇이 막고 있는지를 근거에 적는다.
**막고 있는 것이 사라지면 등급이 붙는다**는 사실을 함께 남긴다.

### 등급을 고르는 법

1. 위반마다 **아래 목록에서 대응하는 항목을 고른다**
2. 그 항목의 등급을 그대로 쓴다
3. 「등급 조정」에 그 항목이 있고 **조건에 해당하면** 적힌 대로 바꾼다. 조건에 없으면 기본등급 그대로다

**조정 규칙이 있는 항목은 해당 여부를 반드시 적는다.** 조건을 따져보지 않고 기본등급을 쓰지 않는다.
해당하지 않으면 `조정 조건 해당 없음` 이라고 한 줄 남긴다 — 빠뜨린 것과 따져본 것을 구별하기 위해서다.

**고를 항목이 없으면 「등급 미정」으로 적고 왜 대응이 없는지 밝힌다.** 임의로 매기지 않는다.
사내 기준에 항목을 더해야 하는 신호이므로 ③에 남긴다.

**조정은 규칙이지 재량이 아니다.** 적혀 있지 않은 이유로 올리거나 내리지 않는다.

**조정으로 상까지 올릴 때는 보상 통제를 먼저 본다.** 다단계 인증, 프로파일 분리, 앞단 차단처럼 그 결함만으로는 경계를 넘지 못하게 막는 것이 **실제로 걸려 있으면 올리지 않는다.**
무엇이 막고 있는지 근거에 적는다. 조정 규칙은 그 통제가 없다는 전제로 쓰여 있다.

## 출력 형식

**다섯 절을 전부 낸다.** ① 요약표 ② 위반 상세 ③ 점검하지 못한 것 ④ 종합 판정 ⑤ 결과 요약 파일.
해당 내용이 없는 절은 "없음"이라고 쓰고, **절 자체를 빠뜨리지 않는다.**
④ 와 ⑤ 가 없으면 읽는 사람이 통과 여부를 스스로 판단해야 하고, 정보보호팀에는 아무것도 가지 않는다.

**① 항목별 한 줄 요약표**

```
1-1  시크릿 fallback   위반 1건  상   K2-6   application.properties:15
1-2  조회 인가         위반 2건  상   K2-2   AttachmentController:91, BoardPageController:40
1-3  요청 크기 상한    위반 1건  미정  —      UserController:41 (대응 항목 없음, ③에 기재)
1-5  캐시 상한         준수      —    —     LoginAttemptService:41 (자동만료, 유계)
1-9  realpath          준수      —    —     AttachmentController:75 (저장명 UUID라 이탈 불가)
1-10 argv 플래그       해당 없음  —    —     외부 명령 실행 지점 없음
0장  확정 안 된 경계    질문 2건  —    —     /ping 노출 범위, 첨부 다운로드 가시성
```

위반이면 **위험도**와 **대응 항목 코드**를 함께 적는다. 위반이 아니면 둘 다 `—`.
**억지로 끼워 맞추지 않는다.** 뜻이 다른 항목에 갖다 붙이느니 「미정」이 낫다.

**② 위반 상세** — `[위험도] 대응 항목 — 파일:줄 — 무엇이 위험한가 — 어떻게 바꿀 것인가`.
**위험도 순으로**(상 → 중 → 하). 위험도는 「위반에는 위험도를 붙인다」의 표에서 읽는다.

```
[상] K2-6 하드코드된 중요정보 — application.properties:15
     서명키가 소스에 기본값으로 박혀 있어 저장소를 읽을 수 있는 사람이 토큰을 위조한다.
     기본값을 없애고 환경변수 미설정 시 기동을 실패시킨다.
```

**③ 점검하지 못한 것** — 대상에서 뺀 파일, 판단하지 못한 항목, 근거가 약한 판정.
**빠짐없이 봤다고 말하지 않는다.** 확인하지 않은 항목을 "준수"로 적지 않는다.

**④ 종합 판정** — 등급별 건수와 그에 따른 처리.

**종합은 아래 넷 중 하나로 적는다.**

| 상황 | 종합 |
|---|---|
| 상이 있다 | **상(N개)이 존재하여 조치 후 재점검 필요** |
| 상은 없고 중이 있다 | **중(N개)이 존재하여 정보보호팀 상의 필요** |
| 상·중이 없다 | **통과** |
| 위 판정에 ③ 이 남아 있다 | 뒤에 **「확인하지 못한 범위 있음」** 을 붙인다 |

**`N` 은 실제 건수로 채운다.** 「상이 있어 재점검 필요」처럼 건수를 빼고 쓰지 않는다 —
1건과 9건은 받는 사람이 해야 할 일의 크기가 다르다.

```
상 2건  →  조치 후 재점검
중 1건  →  플랫폼정보보호팀 상의 필요
하 3건  →  통과
하드닝 4건 (등급 밖)
```

**상이 하나라도 있으면 통과가 아니다.** 건수만 적고 통과 여부를 흐리지 않는다.
다만 **사람을 탓하는 말로 적지 않는다.** 무엇을 하면 통과인지를 적는다 —
「통과 불가」가 아니라 **「조치 후 재점검 필요」**, 「실패」가 아니라 **「보완 필요」**.
점검은 코드를 보는 것이지 만든 사람을 평가하는 것이 아니다.
**③ 에 남긴 것이 있으면 통과라고 쓰지 않는다.** 못 본 범위는 등급이 매겨지지 않았을 뿐이다.

**⑤ 결과 요약 파일** — **점검할 때마다 항상 만든다.** 미정이 없어도, 위반이 0건이어도 만든다.

작업 폴더에 `보안점검-결과-YYYYMMDD-HHMM.txt` 로 쓰고, 리포트 끝에 그 경로를 적는다.
**파일을 만들지 못했으면 만들지 못했다고 적는다.** 만든 척하지 않는다.

**한 항목은 한 줄에 쓴다.** 길다고 줄을 접어 다음 줄로 넘기지 않는다 — 보는 쪽에서
알아서 접힌다. 손으로 접으면 메일에 붙였을 때 줄이 어지럽게 끊긴다.
**줄바꿈은 CRLF** 로 쓴다. 받는 쪽이 Windows 메모장·Outlook 이다.

```
[기준 부재]  ← 사내 기준이 없어 판정 자체를 못 했을 때만
무엇 | 저장 데이터의 보호 요구 수준을 판정하지 못했다
사유 | 사내 개인정보 분류 기준이 확정되지 않아 대조할 기준이 없다

[등급 의견]  ← 등급이 과하거나 모자라다고 볼 때만
항목 | K2-6
사유 | 비운영 프로파일 전용이라 경계가 넘어가지 않는다
```

`이름 | 값` 형태로 쓴다. **값이 아무리 길어도 한 줄이다.** 머리말도 같은 형태다.

**0장에서 답을 못 받은 것은 성격이 둘이다. 갈라서 적는다.**

| | 어디에 | 왜 |
|---|---|---|
| **이 시스템이 정할 것** — 첨부를 누가 볼지, TLS 를 어디서 끝낼지 | 리포트 0장에만. 결과 파일에는 **건수만** | 그 시스템의 정책이라 사내 기준으로 옮길 것이 없다 |
| **사내 기준이 없어 판정을 못 한 것** — 데이터 등급 분류 기준이 없다 | **`[기준 부재]` 블록** | 「등급 미정」과 같다. 정보보호팀이 만들어야 할 것이 있다는 신호다 |

건수만 적고 내용을 안 적으면 받는 쪽이 "5건이 뭔데?" 하고 되묻는다. **담지 않는 이유를 그 줄에 같이 적는다.**

**머리말은 위 여섯 줄이다. 줄을 더하지 않는다.**
점검 항목 수·대상 파일 수·실행 검증 여부·독립성·정책 미확정 건수 같은 **점검 조건은 적지 않는다.**
**하드닝도 적지 않는다.** 등급 밖이라 통과 판정에 영향이 없고, 기존 항목에 이미 대응되므로
표를 넓히는 입력도 아니다. 받는 쪽에서 할 일이 없는 숫자다 — 리포트 ④ 에만 남긴다.
점검을 어떻게 했는지는 **리포트(①~③)에 적고**, 이 파일에는 **무엇이 나왔는지만** 담는다.

**표 버전만 예외로, 파일 맨 끝에 한 줄 적는다.** 사용자가 읽을 것은 아니지만
**어느 표로 매긴 등급인지 알 수 없으면 나중에 판정을 다시 맞춰볼 수 없다.**
표를 고쳐 배포한 뒤 낡은 판을 쓰는 사람을 찾는 단서도 이것뿐이다.

**담는 것은 위가 전부다.** 코드, 파일 경로, 프로젝트·저장소 이름, 사람 이름은 **담지 않는다.**

**「위반 목록」은 `등급 | 항목 코드와 이름 | 한 줄 설명` 이다.** 한 줄 설명에도 **파일명·경로·클래스명·변수명·프로젝트명을 쓰지 않는다.** "`AuthController:76` 에서" 가 아니라 "로그인 실패 기록에" 라고 쓴다.
리포트 ② 의 설명을 그대로 옮기지 말고 **한 줄로 줄이면서 식별되는 부분을 걷어낸다.**

**이 목록이 있어야 정보보호팀이 무엇을 손봐야 할지 안다.** 「상 3건」만으로는 같은 결함 셋인지 다른 셋인지 알 수 없고, 어느 항목이 반복해서 나오는지도 보이지 않는다.
표를 고치는 데 쓰이지 않는 정보이고, 점검 도구가 소스를 실어 나르면 아무도 쓰지 않는다.

그리고 파일 경로와 함께 이 한 줄을 붙인다.

```
이 파일을 플랫폼정보보호팀 / 서동찬 (haru0909@vntgcorp.com) 으로 보내주세요.
기준을 넓히는 데 쓰이며, 보내지 않아도 점검 결과에는 영향이 없습니다.

표 버전 2026-09-18 · 60항목
```

# 고치기 — `--fix`

**`--fix` 가 없으면 코드를 건드리지 않는다.** 찾기만 한다.

`--fix` 가 붙었으면 아래 순서를 지킨다. **순서가 규칙이다.**
**`--fix` 는 상만 고친다.** 중·하·미정은 등급별 처리 규칙이 따로 있다(3단계).

### 1. 리포트를 먼저 전부 낸다

① ② ③ ④ ⑤ 를 **손대기 전 상태로** 낸다. 고치면서 판정하면 「원래 준수」와 「고쳐서 준수」가
구분되지 않고, 그러면 ① 표 전체가 근거를 잃는다. **리포트는 수정 전 스냅샷이다.**

### 2. 되돌릴 수 있는 자리에서 고친다

대상은 **이미 돌아가는 시스템**이다. 고치기 전에 되돌릴 수단부터 만든다.

**고칠 파일의 원본을 먼저 한 폴더에 복사한다.** 한 파일이라도 고치기 전에 한다.

```
<프로젝트 최상위>/보안점검-수정전-YYYYMMDD-HHMM/
    src/main/java/com/company/board/web/AuthController.java
    src/main/resources/application.properties
```

**원래 경로 구조를 그대로 유지한다.** 되돌릴 때 폴더째 덮어쓰면 끝나야 한다.
파일 옆에 `.bak` 를 뿌리지 않는다 — 소스 트리가 지저분해지고 배포물에 섞인다.

리포트 끝에 이렇게 안내한다.

```
.\보안점검-수정전-20260911-1430\ 파일이 이전 파일입니다.
```

**한 줄로 끝낸다.** 덮어쓰라거나 지우라고 시키지 않는다 — 어떻게 쓸지는 받는 사람이 정한다.

**백업을 만들지 못했으면 고치지 않는다.** 되돌릴 수 없는 수정은 하지 않는다.

**이 스킬은 배포하지 않는다.** 파일을 고칠 뿐이고, **운영 반영은 사람이 정한다.**
고친 것을 운영에 올리는 절차(테스트·승인)는 원래대로 남아 있다.

### 3. 무엇을 고치고 무엇을 안 고치는가

**기본은 상만 고친다.** 등급별 처리 규칙이 이미 정해져 있고, `--fix` 는 그 규칙을 대신하지 않는다.

| 등급 | `--fix` | 왜 |
|---|---|---|
| **상** | **고친다** | 통과를 막는 등급이다. 고치는 것 외에 선택지가 없다 |
| **중** | **안 고친다** | **정보보호팀 상의 대상**이다. 고쳐버리면 상의할 것이 없어지고, 보상 통제를 감안한 조정 기회도 사라진다 |
| **하** | **안 고친다** | **통과 등급**이다. 악용 경로가 없는 것을 고치려고 운영 코드를 건드리는 것은 위험 대비 이득이 맞지 않는다 |
| **미정** | **안 고친다** | 사내 기준에 **항목이 없다.** 그것이 결함인지를 회사가 아직 정하지 않았다. 정하기 전에 고치면 기준 없이 코드를 바꾼 것이고, 사례가 수집되지 않아 표도 자라지 않는다 |
| **하드닝** | **안 고친다** | 위반이 아니다 |

**사용자가 지시하면 고친다.** "중도 같이 고쳐줘", "하까지 고쳐줘" 라고 하면 고치고, ⑥ 에 **사용자 지시로 고쳤음**을 적는다. 묻지 않고 범위를 넓히지 않는다.

**상이 0건이면 고칠 것이 없다.** 그렇게 적고, 중·하·미정 목록을 보여주며 **지시하면 고친다고 안내한다.**

### 안 고치는 것이 하나 더 있다

**0장이 안 정해진 항목에 걸린 위반은 상이어도 고치지 않는다.** 공개 범위를 모르는데 인가를 좁히면
기능이 깨지고 넓히면 취약점이 된다. 어느 쪽으로 고쳐도 틀린다.
③ 에 남기고 **무엇을 정해줘야 고칠 수 있는지** 적는다.

### 4. ⑥ 수정 내역을 낸다

```
⑥ 수정 내역

[상] K2-6 — application.properties:15
     기본값 제거, 미설정 시 기동 실패하도록 변경
     우회 시험: 빈 값 / 짧은 값 / 다른 프로파일로 기동 → 전부 기동 실패

고치지 않음
[상] K2-2 — 조회 인가. 0장 「외부 공개 범위」가 정해져야 고칠 수 있다
[중] K4-1 — 계정 열거. 정보보호팀 상의 대상
[하] K4-3 — 예외 처리. 통과 등급
[미정] 로그 위조 — 사내 기준에 항목이 없다

중·하·미정도 고치길 원하시면 말씀해 주세요.
```

**리포트의 위반과 한 건씩 대응시킨다.** 대응이 없는 수정이 있으면 그것도 적는다.
**수정마다 「우회 시험」 한 줄을 붙인다** — 무엇을 던져봤는지 쓰지 못하면 5단계를 건너뛴 것이다.

### 5. 고친 것을 공격해 본다

**수정으로 들어온 코드도 1장 순회 대상이다.** 방어 장치를 새로 넣었다면 그 장치 자체가
새 결정 지점이고, 새 자원이고, 새 예외 경로다. 원래 결함만 재현해 보고 닫혔다고 적으면
그 안에 같이 들어온 구멍이 다음 회차까지 남는다.

수정한 방어마다 셋을 확인한다.

| 확인 | 묻는 말 |
|---|---|
| **면제 조건** | 이 방어를 건너뛰는 조건이 무엇이고, **그것을 요청자가 정할 수 있는가.** 헤더·확장자·파라미터로 적용 여부가 갈리면 그 자체가 우회로다 |
| **한계 동작** | 이 방어에 용량·개수·시간 상한이 있는가. 그 상한에 닿았을 때 **열리는가 닫히는가.** 열리면 상한을 채우는 것이 곧 방어 해제다 |
| **적용 대상** | 이 방어가 벌하는 쪽이 공격자인가, 같은 조건을 공유하는 제3자인가 (**1-23**) |

**정직한 클라이언트로만 시험하지 않는다.** 정상 요청이 통과하고 원래 공격이 막히는 것은
최소 조건이지 확인이 아니다. 헤더를 속이고, 동시에 던지고, 상한을 채워 본다.

실제로 한 회차에서 상 3건을 고친 뒤 정상 요청과 원래 공격만 재현해 「닫힘」으로 적었는데,
다음 회차에서 상 1·중 2가 새로 나왔다 — 세 건 모두 방금 넣은 방어 장치 안에 있었다.

### 6. 기능이 깨졌는지 본다

테스트가 있으면 **돌리고 결과를 적는다.** 없으면 **아무 말도 적지 않는다** — 없는 것을 매번 알릴 필요는 없다.
보안을 고치다 서비스를 멈추는 것이 가장 나쁜 결과다.

### 7. 재점검은 새 세션에서

**같은 세션에서 다시 점검하지 않는다.** 방금 고친 것을 알고 보면 통과시키는 쪽으로 기운다.
리포트 끝에 새 세션에서 `/vsecu-review` 를 다시 돌리라고 적는다.

**결과 파일(⑤)은 덮어쓰지 않고 위에 쌓는다.** 수정 전 내용을 경계선 아래에 그대로 두고,
경계선 위에 수정 회차 블록을 새로 적는다. 받는 사람이 맨 위에서 현재 상태를 보고,
필요하면 내려가서 그 전에 무엇이 있었는지 본다.

**수정 전 블록의 숫자는 절대 고쳐 쓰지 않는다.** 그 값은 점검이 내린 판정이고, 고친 사람이
스스로 0으로 바꾸면 통과 도장을 스스로 찍는 것이 된다.

**「종합」에 「통과」를 쓰지 않는다.** 상·중을 전부 고쳤더라도 새 세션 재점검 전까지는
**「새 세션 재점검 대기」** 다. 「남은 위험도」에는 `자체 집계` 라고 명시한다.

```
[보안점검 결과 — 수정 회차]
수정일 | 2026-09-15 10:10
고침 | 상 1 · 중 2 · 미정 2
보류 | 미정 1 (위임 대상 정보 부족)
남은 위험도 | 상 0 · 중 0 · 미정 1 (자체 집계 — 독립 재점검 전이므로 통과가 아니다)
우회 시험 | 함 (고친 방어마다 면제 조건·한계 동작·적용 대상을 직접 공격)
종합 | 새 세션 재점검 대기

[수정 목록]  ← 고친 것만. 등급 순으로 한 줄씩. 파일명·클래스명은 여기에도 쓰지 않는다
상 | V-5 요청 본문·업로드 크기 상한 없음 | 상한 적용 여부를 클라이언트 헤더가 아니라 요청 경로로 정하도록 바꿨다
중 | K2-16 반복된 인증시도 제한 기능 부재 | 지연을 걸 여력이 없으면 검증 자체를 거부하도록 바꿨다

================================================================
아래는 수정 전 점검 결과다. 고치지 않고 그대로 둔다.
================================================================
```

## 자동 생성 결과물에서 특히 자주 나오는 형태

문법적으로 정상이고 테스트도 통과하지만 취약하다. **의식적으로 확인할 것.**

1. **시크릿에 개발용 기본값** (1-1)
2. **조회 API·렌더 페이지의 인가 누락** (1-2)
3. **전부 읽은 뒤 상한 검사** (1-3)
4. **상한을 통과한 뒤 곱셈에서 넘침** (1-4)
5. **상한 없는 캐시** (1-5)
6. **보상 코드로 트랜잭션을 대신함** (1-6)
7. **의존성을 피하려고 직접 구현** (적용 원칙 2)
8. **경계를 묻지 않고 넓은 쪽으로 결정** (0장)
9. **교차 출처 설정을 넓게 열기** — "브라우저에서 호출이 안 된다"를 가장 빠르게 없애는 방법이기 때문
10. **응답에 모델 전체 직렬화** — 비밀번호 해시, 내부 플래그, 권한 정보가 함께 나간다
11. **존재하지 않는 패키지 이름**
12. **검증·보안 기능 해제로 문제 회피** — 인증서 검증 끄기, 이스케이프 해제, 디버그 모드 유지
13. **업로드 타입을 클라이언트가 보낸 값으로만 판정** (1-15)
14. **발급한 세션·토큰을 무효화할 수단이 없음** (1-16)
15. **샘플 데이터가 프레임워크 관례로 운영에도 자동 로드됨** (1-17)
16. **클라이언트 오류가 500으로 처리되며 스택트레이스가 무제한 로깅됨** (1-18)
17. **필터·미들웨어의 오류 응답이 표준 오류 라우팅을 거치며 뒷단에서 뒤바뀜** (1-19)
18. **자체 로그인에 반복 시도 제한이 없음** (1-20)
19. **자체 로그인의 응답 시간으로 계정 존재 여부가 드러남** (1-21)
20. **보안 이벤트(로그인 실패 등)를 감사 로그로 남기지 않음** (1-22)
21. **반복시도 제한을 계정 축에도 잠금으로 걸어, 그 잠금 자체가 다른 사용자를 잠그는 공격 수단이 됨** (1-23)
22. **배포·공유 범위를 넓은 채로 둠** — 시트·폼·스크립트 웹앱은 코드에 인증이 없어 설정이 유일한 경계다 (1-24)

# 영역별 상세 기준

## 1. 외부 입력 — 인젝션

사용자 입력, 요청 파라미터, 헤더, 쿠키, 업로드 파일명, 외부 API 응답, DB에서 읽은 값은 **모두 신뢰할 수 없는 입력**이다.

**인젝션은 "입력이 어디로 흘러 들어가는가(싱크)"로 판단한다.** 싱크마다 안전한 API가 따로 있다.

| 싱크 | 반드시 이렇게 | 하지 말 것 |
|---|---|---|
| **SQL 질의** | **바인딩 변수(Prepared Statement / Parameterized Query)** 로 값을 전달. ORM의 파라미터 바인딩 사용 | 문자열 연결·보간으로 질의문 조립 |
| 동적 테이블·컬럼명 | 바인딩이 불가하므로 **허용 목록에 있는 값인지 검사한 뒤** 사용 | 입력값을 질의문에 그대로 삽입 |
| `LIKE` 검색 | 바인딩 + **와일드카드 문자 이스케이프**. 바인딩만으로는 사용자가 넣은 `%` `_` 가 여전히 와일드카드로 동작해 전체 데이터를 긁을 수 있다 | 바인딩만 하고 끝 |
| **운영체제 명령** | **셸을 거치지 않고 인자 배열로 실행.** 필요한 명령이 정해져 있으면 허용 목록으로 고정. **인자 배열만으로는 부족하다 — 1-10(플래그 스머글링), 1-11(환경변수)을 함께 적용** | 셸에 문자열을 넘기는 실행, 입력을 이스케이프해서 넘기기 |
| 셸 래퍼 함수 | 내부에서 셸을 쓰는 사내 헬퍼(`run()`, `shell()`, `sudo()`)는 `os.system` 과 **같은 싱크**다. 이름이 안전해 보여도 본문을 확인한다 | 래퍼라는 이유로 안전하다고 가정 |
| 동적 코드 실행 | 외부 입력이 도달하지 않게 설계를 바꾼다 | 입력을 평가·컴파일·동적 로딩에 전달 |
| NoSQL / LDAP / XPath | 각 기술의 **파라미터화 API** 사용. 연산자·구조가 입력으로 결정되지 않게 한다 | 질의 문자열·질의 객체에 입력을 그대로 병합 |
| **XML 파서** | **외부 개체·DTD 처리를 끈다.** 파서 기본값이 허용인 경우가 많아 명시적으로 비활성화해야 한다 | 외부에서 받은 XML 을 기본 설정 파서로 처리 (파일 유출·내부망 접근·엔티티 폭탄) |
| XML 문서 생성·수정 | 값은 이스케이프하거나 API 로 노드를 만든다 | 문자열 연결로 XML 조립 (구조를 바꿔치기당함) |
| **보안 판단에 쓰이는 값** | **서버가 보유한 값으로 판단한다.** 권한·등급·가격·상태는 요청에서 받지 않는다 | 헤더·쿠키·파라미터·숨은 필드의 값으로 인증·인가·금액을 결정 |
| 클라이언트가 정할 수 있는 헤더 | `X-Forwarded-For`, `X-Real-IP`, `Host`, `Origin`, `Referer`, 커스텀 `X-User-*` 로 **권한을 부여하지 않는다.** 신뢰하려면 앞단 프록시가 덮어쓰는지 확인한다 | 헤더 값으로 접근 허용 결정 |
| **서버측 템플릿** | 템플릿은 **개발자가 작성한 것만** 쓰고, 데이터는 변수로 전달 | 사용자 입력으로 템플릿 문자열을 만들거나 렌더 |
| **HTTP 헤더·리다이렉트 주소** | 개행·제어문자 제거, 이동 대상은 **허용 목록** | 입력을 헤더값·`Location` 에 그대로 반영 |
| **로그** | 개행·제어문자를 제거하거나 구조화 로깅(필드 분리) 사용 | 입력을 로그 문장에 그대로 이어 붙이기 |
| **LLM·에이전트 컨텍스트** | 제어문자·개행을 제거하고 길이를 제한한 뒤 싣는다. 모델에게 컨텍스트는 **지시문으로 읽힐 수 있는 싱크**다 — 파일명, 로그 줄, 도구 출력, 저장소 안의 파일 내용은 우리가 정한 값이 아니다 | 외부에서 온 문자열을 그대로 프롬프트·시스템 메시지·도구 결과에 넣기 |
| 파일 포함·모듈 로딩 | 대상을 **허용 목록**으로 고정 | 입력으로 포함 경로·모듈명 결정 |
| 값 검증 | **타입·길이·형식·범위를 양성 조건으로 정의**하고 불일치 시 거부 | 위험 문자·패턴을 제거하거나 치환 |
| 역직렬화 | **데이터 전용 포맷(JSON 등) + 스키마 검증.** 신뢰되지 않은 입력을 객체로 복원하지 않는다. 크기·깊이 상한은 **1-3** | 언어의 객체 역직렬화 기능에 외부 입력 전달 |

> **공격 변종이 달라도 방어는 같다.** SQL 인젝션의 오류 기반·UNION 기반·블라인드·시간 지연은 공격자의 탐지 방식 차이일 뿐, 만드는 쪽의 대응은 **바인딩 변수 하나**다. 변종별 대응을 찾지 말고 근본 통제를 적용한다.
>
> 단 **오류 기반 공격은 오류 상세가 노출돼야 성립**한다. 11장(오류 비노출)이 함께 지켜져야 한다.

**CI 워크플로도 같은 싱크다.** GitHub Actions 의 `run:` 에 이슈 제목·PR 본문·커밋 메시지·`client_payload.*` 를 보간하지 않는다. `env:` 블록으로 전달하고, `ref:` 에 넣는 값은 형식을 검증한다.

## 2. 출력 — XSS

**입력 시점 필터링에 의존하지 않는다.** 같은 값이라도 출력되는 위치마다 안전한 형태가 다르므로 **출력 지점에서** 처리한다.

| 형태 | 경로 | 이것 때문에 달라지는 대응 |
|---|---|---|
| **반사형** | 요청에 실린 값이 그 응답에 그대로 나온다 | 아래 출력 위치별 인코딩으로 막힌다 |
| **저장형** | 값이 저장된 뒤 **다른 사용자**에게 렌더된다 | **저장 시점이 아니라 렌더 시점에** 처리한다. 피해가 본인이 아니라 다른 사용자(관리자 포함)에게 가므로 영향이 가장 크다 |
| **DOM 기반** | 서버를 거치지 않고 브라우저 안에서 발생한다 | **서버측 방어가 전혀 통하지 않는다.** 주소 일부·페이지 간 메시지·로컬 저장값을 신뢰할 수 없는 입력으로 취급하고, 클라이언트에서 HTML로 삽입하지 않는다 |

| 출력 위치 | 반드시 이렇게 |
|---|---|
| HTML 본문 | **텍스트로 삽입**(문자열이 아니라 텍스트 노드), 또는 HTML 엔티티 인코딩 |
| HTML 속성 | 속성값 인코딩 + **반드시 인용부호로 감싸기** (인용부호 없는 속성은 인코딩해도 우회된다) |
| 링크·리소스 주소 | URL 인코딩 + **스킴 검증**. URL 파서로 정규화한 뒤 허용 스킴만 통과 (문자열 앞부분 비교는 우회된다) |
| 스크립트 영역 | 삽입하지 않는다. 데이터는 구조화된 형태로 전달 |
| 이벤트 핸들러 속성 | HTML 이스케이프만으로 부족하다. 브라우저가 속성값을 HTML 디코딩한 뒤 실행하므로 `&#x27;` 이 다시 `'` 가 된다 |
| 스타일 영역 | 삽입하지 않는다 |

- **이스케이프 함수는 따옴표까지 인코딩해야 한다.** `<` `>` `&` 만 처리하는 함수는 속성 컨텍스트에서 무력하다. "textContent 에 넣고 innerHTML 을 읽는" 관용구도 같은 결함이다.
- **템플릿 엔진의 자동 이스케이프를 끄지 않는다.** 해제 기능(`|safe`, `mark_safe`, `<%- %>`, 삼중 중괄호, `dangerouslySetInnerHTML`, `v-html`)을 사용하지 않는다. Jinja 는 raw `Environment()` 에서 기본이 꺼져 있고, Go 는 `text/template` 이 아니라 `html/template` 을 써야 한다.
- **서버에서 HTML을 문자열로 조립하지 않는다.** 템플릿 엔진을 쓴다. 조립하면 보간 지점 하나만 빠져도 알아채기 어렵고, 후처리 단계가 이미 만들어진 태그 속성 안으로 파고들 수 있다.
- **HTML 서식을 살려야 하는 요구사항이 있으면** 금지가 아니라 **검증된 정화 라이브러리(sanitizer)를 통과시킨 뒤** 삽입한다. 허용 태그·속성은 명시적 최소 목록으로 하고, 이벤트 핸들러 속성과 스타일 속성은 허용하지 않는다.
- 정화 라이브러리는 **유지보수되고 있는 것**을 쓴다. XSS 방어를 통째로 위임하는 부품이므로 방치된 라이브러리는 새 우회 기법에 대응하지 못한다.
- **정화 함수의 대상과 싱크가 맞는지 확인한다.** CSV 수식 접두사를 제거하는 `sanitizeCsvValue()` 를 통과한 값이 HTML 싱크로 가면 아무 방어도 되지 않는다. 이름이 안전해 보이는 것이 오히려 신호다.
- 마크다운·리치텍스트 렌더링은 원시 HTML 허용 옵션을 끈다.
- **한 필드에 정화를 추가했으면 같은 싱크에 도달하는 형제 필드를 전부 확인한다.**
- HTML 을 반환하는 응답에는 CSP, 타입 추측 방지, 프레임 삽입 제한 헤더를 설정한다.

## 3. 파일과 경로

| 항목 | 반드시 이렇게 |
|---|---|
| 경로 조립 | **정규화한 뒤 기준 디렉터리를 벗어났는지 검사.** 상위 경로 문자열을 제거·치환하는 방식은 우회된다 |
| 심볼릭 링크 | `resolve()`·`Clean()`·`normalize()` 는 **렉시컬**이라 링크를 따라가지 않는다. **`realpath` 로 실경로를 구한 뒤** 기준 디렉터리의 실경로와 비교한다 |
| 이탈 검사 방법 | 단순 문자열 접두사 비교는 위험하다(`/app/data` 기준에서 `/app/data-evil` 통과). 경로 컴포넌트 단위 비교 또는 상대경로 계산을 쓴다 |
| 절대경로 입력 | 경로 결합 함수가 **절대경로를 받으면 기준 디렉터리를 무시**하는 언어가 있다. 결합 후 반드시 이탈 검사 |
| 업로드 파일명 | **원본 파일명을 저장 경로에 쓰지 않는다.** 서버가 이름을 생성. 원본명은 표시용으로 별도 저장 |
| 업로드 타입 검사 | 확장자나 클라이언트가 보낸 타입이 아니라 **실제 내용으로 판정** |
| 실행 가능 콘텐츠 | HTML·SVG·스크립트는 이미지로도 허용하지 않는다(저장형 XSS 경로) |
| 크기 제한 | **읽는 중 누적 검사.** 전부 읽은 뒤 크기를 재면 이미 자원을 소모한 뒤다 (**1-3**) |
| 저장 위치·권한 | 웹으로 직접 서비스되지 않는 위치, 실행 권한 없이 저장 |
| 다운로드 응답 | 첨부로 내려보내고 콘텐츠 타입 추측을 막는다. 저장된 콘텐츠 타입을 그대로 반사하지 않는다 |
| **압축 파일 해제** | 항목별로 **경로 이탈 검사**를 하고, 해제 후 총 크기·항목 수 상한을 둔다 |
| **중요 자원 권한** | 설정 파일·키 파일·로그·업로드 디렉터리는 **필요한 주체만 접근**하도록 권한을 좁힌다. 기본 권한에 의존하지 않는다 |
| 자격증명 파일 생성 | 소유자 전용 권한(0600 / 0700)을 **생성 시점에** 지정한다. 만든 뒤 권한을 바꾸는 방식은 그 사이에 노출되고, 이미 열린 파일 디스크립터를 회수하지 못한다 |

## 4. 인증

| 항목 | 반드시 이렇게 |
|---|---|
| 비밀번호 저장 | **비밀번호 전용 해시**(느린 해시, 솔트 포함)를 쓴다. 범용 고속 해시는 단독으로 쓰지 않는다 |
| 토큰·세션 | 만료를 두고, **무효화 수단**을 갖춘다(비밀번호 변경·로그아웃 시 기존 세션 폐기) |
| 세션 쿠키 | 스크립트 접근 차단, 보안 채널 전용, 크로스사이트 전송 제한 속성을 설정 |
| 서명 검증 | 허용 알고리즘을 **코드에서 고정**한다. 토큰이 스스로 알려주는 알고리즘을 신뢰하지 않는다 |
| 검증 순서 | 서명을 먼저 검증하고 그 다음에 페이로드를 파싱한다. 만료·주체 확인은 서명 검증 이후다 |
| 인증서 검증 | **끄지 않는다.** 사설 인증기관이 필요하면 신뢰 저장소에 등록한다. 검증 항목은 **호스트명 일치**(인증서의 CN·SAN과 실제 접속 호스트), 신뢰된 발급기관의 서명, 유효기간, **해지 여부**, 안전한 알고리즘 사용이다 — 라이브러리에 따라 체인은 검증하면서 **호스트명 확인을 생략**하는 기본값이 있으므로 명시적으로 확인한다 |
| 실패 응답 | 아이디와 비밀번호 중 무엇이 틀렸는지 **구분하지 않는다**. **처리 시간으로도** 구분되지 않게 한다 — 계정이 없을 때도 더미 해시 검증을 수행해 응답 시간을 맞춘다. **로그인을 SSO에 위임했다면 해당 없음**(1-21) — 앱이 직접 비밀번호를 비교하는 지점이 없다 |
| **반복 시도 제한** | 실패 횟수를 세어 **지연·잠금·추가 확인**을 적용한다. 계정 축에는 지연·추가 확인, 출처(IP) 축에는 잠금을 건다 — 계정 축까지 잠그면 그 잠금 자체가 다른 사용자를 잠그는 공격 수단이 된다(**1-23**). **로그인을 SSO에 위임했다면 해당 없음**(1-20) — SSO 제공자가 이미 처리한다 |
| 비밀번호 정책 | **NIST SP 800-63B 기준을 따른다.** 최소 길이(8자 이상, 길수록 권장)를 강제하고 **알려진 유출 목록·사전 단어·반복/연속 문자·서비스명 등 문맥 단어를 거부**한다. **문자 조합 규칙(대문자·특수문자 필수 등)을 강제하지 않고**, **주기적 변경을 요구하지 않는다** — 유출 정황이 확인될 때만 변경시킨다. 긴 비밀번호와 모든 출력 가능 문자를 허용하고 **붙여넣기를 막지 않는다**(비밀번호 관리자 사용을 방해하지 않기 위함). 비밀번호 힌트와 지식기반 질문(가장 좋아하는 색 등)을 쓰지 않는다 |
| 다단계 인증 | 우회 경로가 없는지 확인한다 — 1차 인증만으로 접근되는 엔드포인트가 남지 않게 한다 |
| 세션 발급 | 로그인 시 **새로 발급**하고 권한이 바뀌면 재발급한다. 클라이언트가 제시한 식별자를 그대로 세션으로 채택하지 않는다 |
| OAuth `state` | 추측 불가능해야 하고 **세션에 바인딩**되어야 한다. 서명 검증이나 세션 대조 없이 디코딩만 하는 구조에서는 공격자가 원하는 값을 써 넣을 수 있으므로, 그 값을 비교하는 코드는 아무 일도 하지 않는다 |
| 토큰 발급 엔드포인트 | 자격증명을 반환하는 핸들러가 요청 본문·질의 문자열만 읽고 인증 주체를 확인하지 않는지 본다 |

**비밀번호 재설정·계정 복구.** 자체 로그인을 구현하면 반드시 따라오는 흐름이고, 모델이 기본값으로 자주 틀리는 지점이다.

- 재설정 링크의 호스트를 요청의 `Host` 헤더로 만들지 않는다 — 공격자가 헤더를 조작하면 피해자의 재설정 토큰이 공격자 도메인으로 배달된다. 링크 주소는 서버 설정값으로 고정한다.
- 재설정 토큰을 DB에 평문으로 저장하지 않는다 — 해시해서 저장한다. DB가 읽히면 그 값 자체가 로그인 수단이 된다.
- 토큰은 1회용 + 짧은 만료로 하고 사용 즉시 폐기한다. 비밀번호가 바뀌면 그 계정의 기존 세션·토큰을 전부 폐기한다(**1-16**).
- 재설정 요청에 대한 응답은 계정 존재 여부와 무관하게 동일하게 한다.
- 재설정 페이지에서 외부 리소스(이미지·스크립트 등)를 불러오지 않는다 — 토큰이 담긴 주소가 `Referer` 로 그 리소스 서버에 새어 나간다.

**계정 열거는 로그인 실패 응답에만 있지 않다.** 회원가입의 "이미 사용 중인 아이디입니다" 메시지, 아이디 중복확인 API, 비밀번호 재설정의 응답 차이가 모두 같은 문제(**1-21**)다. 로그인 외의 엔드포인트도 같은 기준으로 점검한다.

## 5. 인가

**인증과 인가는 다르다. "로그인했으니 통과"는 인가가 아니다.**

- 모든 요청에서 **"이 주체가 이 리소스에 이 동작을 할 권한이 있는가"** 를 리소스 접근 직전에 검사한다.
- 검사는 **서버에서** 한다. 화면에서 버튼을 숨기는 것은 인가가 아니다.
- 대상 리소스의 식별자를 **요청에서 받되 소유권은 서버가 확인**한다. 권한이 없으면 존재 여부도 노출하지 않는다.
- **읽기에도 적용한다.** 쓰기에는 소유자 검사가 있는데 조회·다운로드·페이지 렌더에는 없는 비대칭이 흔하다 (**1-2**).
- 인증 정보를 주입해놓고 인가 판단에 쓰지 않으면 그 자체가 누락 신호다.
- **목록 질의는 현재 주체의 범위로 필터링한다.** 다중 사용자 시스템에서 필터 없는 전체 조회는 인가 우회다.
- **요청 본문의 외래 키도 확인한다** — 다른 사용자의 리소스 ID 를 참조할 수 있는지 본다. 선택 목록(드롭다운)에 권한 없는 항목이 나오는 것도 같은 문제다.
- **형제 핸들러와 비교한다.** 같은 파일의 다른 핸들러가 소유권·멤버십·출처를 검사하는데 이 핸들러만 하지 않는다면, 그 누락이 취약점이다.
- **새로 만든 인가 게이트가 fail-open 인지 본다.** 조건이 거짓일 때 그냥 통과하면, 그 게이트가 유일한 제약이었던 경로가 무방비가 된다.

## 6. 요청 데이터 매핑

- **요청 본문을 모델·엔티티에 통째로 매핑하지 않는다.** 수정 가능한 항목을 명시적으로 정의하고 그것만 반영한다.
- 권한·소유권·상태·금액·식별자 항목은 **어떤 경우에도 클라이언트 입력으로 결정되지 않는다.**
- 방향은 **허용 목록**이다. "위험한 항목을 제외"하는 방식은 나중에 항목이 추가될 때 자동으로 뚫린다.
- **응답도 같다.** 내부 모델을 그대로 직렬화하지 말고 노출할 항목을 정의한다.
- **중첩·연관 레코드는 부모의 권한이 아니라 보는 사람의 권한으로 거른다.** 공개 컬렉션에 담긴 비공개 항목이 그대로 나가는 형태가 흔하며, 이 결함은 라우트가 아니라 직렬화 메서드에 산다.
- **불리언·숫자 변환을 확인한다.** 폼 데이터는 전부 문자열이라, 언어에 따라 `"false"` 가 참으로 평가된다. 명시적으로 파싱한다.

## 7. 시크릿과 설정

- **기본값(fallback)을 두지 않는다.** 값이 없으면 **기동 시점에 실패**시킨다(Fail-Closed). 기본값이 있으면 운영에서 설정을 누락해도 정상 기동하고, 그 순간부터 **누구나 아는 값을 쓰는 상태**가 된다. 하드코딩은 도구가 잡지만 이 형태는 잡기 어려워 더 오래 남는다 (**1-1**).
- 키·비밀번호·토큰·인증정보를 **코드·저장소에 두지 않는다.** 테스트 코드, **주석**, 설정 예시, 초기화 스크립트도 같다. 주석에 남은 계정·내부 주소·검증 우회 메모는 그대로 유출 경로가 된다.
- **중요정보는 저장할 때도 보호한다** — 개인정보·인증정보·결제정보는 평문으로 두지 않는다. 무엇이 중요정보인지 불분명하면 확인한다.
  > **사내 기준 확인 필요**: 아래는 회사의 개인정보·중요정보 분류 기준이 확정되면 채울 자리다. 확정 전까지는 이 스킬이 항목을 임의로 단정하지 않는다 — 판단이 서지 않으면 **「확인 불가」로 올린다**(vsecu-review 4가지 판정 참고).
  >
  > | 분류 | 예시 | 처리 기준 |
  > |---|---|---|
  > | *(사내 개인정보보호 담당 기준 반영 예정)* | | |
- **클라이언트에 중요정보를 남기지 않는다** — 만료가 긴 쿠키, 브라우저 저장소, 캐시 가능한 응답에 인증정보·개인정보를 넣지 않는다.
- 검증은 요청 처리 시점이 아니라 **기동 시점**에 한다.
- **발급하는 자격증명은 알려진 접두사 규칙을 따른다.** 임의 형식을 쓰면 시크릿 스캐너와 로그 마스킹 규칙이 인식하지 못해, 이미 마련된 유출 방지 장치를 통과해 버린다.
- 안전한 기본 상태로 시작한다 — 접근 제어는 **기본 거부**, 기본 계정·샘플 콘텐츠 제거, 관리 기능은 외부 노출 금지, 운영에서 디버그 모드 해제.

## 8. 암호·해시·난수

- **암호 기능을 직접 구현하지 않는다.** 검증된 라이브러리의 고수준 API를 쓴다.
- **폐기된 알고리즘을 쓰지 않는다.** 현행 권고 알고리즘과 **충분한 키 길이**를 쓴다. 무엇이 현행인지 불확실하면 확인한다. ECB 모드를 쓰지 않는다.
- 인증된 암호화 모드를 쓰고, 초기화 벡터·논스를 재사용하지 않는다.
- **키 관리를 설계에 포함한다** — 생성·보관·접근 통제·교체·폐기. 키를 코드·설정 파일·저장소에 두지 않는다.
- **예측 불가능성이 필요한 값**(토큰, 세션 식별자, 재설정 키, 저장 파일명, 쿠폰·초대 코드)에는 **암호학적 난수**를 쓴다. 일반 난수 생성기를 쓰지 않는다.
- **길이를 확인한다.** 접근을 통제하는 값은 128비트 이상, 추측을 막아야 하는 값은 64비트 이상. **난수원이 안전해도 출력을 잘라 쓰면 무의미하다** — UUID 앞 8자는 32비트다 (**1-7**).
- 비밀번호 해시에는 **솔트를 반드시 포함**한다(라이브러리가 처리하는지 확인).
- 비밀 값 비교는 **상수시간 비교**를 쓴다.
- **전자서명·무결성 검증을 생략하지 않는다** — 외부에서 받은 코드·업데이트·설정·패키지는 서명이나 해시로 검증한 뒤 사용한다.

## 9. 통신과 브라우저 설정

| 항목 | 반드시 이렇게 |
|---|---|
| 전송 구간 | 외부 통신은 암호화 전용. 신뢰 경계를 넘는 내부 통신도 암호화 |
| **교차 출처 허용(CORS)** | **허용 출처를 정확히 일치하는 목록으로 명시.** 요청의 출처를 그대로 되돌려주지 않는다 |
| 출처 비교 | 부분 일치·접미사 비교는 위험하다(유사 도메인 통과). 느슨한 정규식도 같다. URL 파서로 정규화한 뒤 **호스트만** 비교한다 — `netloc` 에는 `user:pass@` 가 포함된다 |
| 와일드카드 | 자격증명을 함께 허용하는 API에는 **와일드카드를 쓰지 않는다.** 프레임워크가 이를 출처 반사로 바꿔 처리하는 경우가 있어 "브라우저가 막아주겠지"에 기대면 안 된다 |
| 상태 변경 요청 | 쿠키로 인증하는 구조라면 **CSRF 대응**(토큰 + 쿠키 전송 제한 속성)을 둔다. 헤더 기반 인증만 쓰는 API는 해당 없음 |
| 응답 헤더 | 콘텐츠 보안 정책, 타입 추측 방지, 전송 보안 강제, 프레임 삽입 제한, 참조자 정책을 설정 |
| **서버가 보내는 요청** | 사용자가 지정한 주소로 서버가 요청하지 않는다. 필요하면 허용 도메인 목록 + **DNS 해석 결과 전체**에 대해 내부망(사설·루프백·링크로컬 169.254.0.0/16 메타데이터) 차단 + 리다이렉트 제한 |
| 리다이렉트 | 허용 목록 통과 후에도 3xx 자동 추적으로 되살아난다. 수동 처리하고 **매 홉을 재검증**한다 |
| 도달성 확인 | 응답 본문을 가져오지 않는 ping·헬스체크도 **내부망 지도를 그려준다.** 인증과 대상 제한을 건다 |
| 신뢰 경계 밖 URL | 형식·스킴만 검사하는 `validate_url` 은 방어가 아니다. 저장소의 설정 파일·매니페스트에 담긴 URL 도 공격자가 쓴 값일 수 있다 |

> **교차 출처 설정은 인가가 아니다.** 좁혔다고 인가 검사를 생략하지 않는다. 브라우저가 아닌 클라이언트는 이 제약을 받지 않는다.

## 10. 의존성

- **처음 보는 패키지는 실제로 존재하는지 확인한다.** 이름이 그럴듯해도 존재하지 않을 수 있고, 공격자가 그 이름을 선점해두는 수법이 있다.
- 도입 전 확인: 이름이 정확한가(유사 이름 혼동), 유지보수되고 있는가, 알려진 취약점이 있는가, 기존 의존성이나 표준 라이브러리로 대체 가능한가.
- **버전을 고정하고 잠금 파일을 저장소에 포함**한다. 컨테이너 이미지는 변경 불가한 식별자로 고정한다.
- **서드파티 CI 액션은 SHA로 고정한다.** 쓰기 권한이나 시크릿에 접근하는 워크플로에서 태그·브랜치 참조는 언제든 내용이 바뀔 수 있다.
- 취약점 점검을 정기적으로 수행하고, 예외는 사유와 기한을 기록한다.
- **의존성을 늘리지 않으려고 직접 구현하는 것은 이 장의 회피가 아니라 더 큰 위험이다.** **적용 원칙 2**를 우선한다.

## 11. 로깅과 오류

- 비밀번호·토큰·세션 식별자·인증정보·개인식별정보·결제정보·**요청 본문 전체**를 로그에 남기지 않는다. 필요하면 가린 뒤 기록한다.
- **자격증명을 URL 질의 문자열에 넣지 않는다** — 접근 로그·리퍼러·브라우저 히스토리에 남는다.
- 사용자 응답에 **내부 정보를 노출하지 않는다** — 스택 추적, 질의 오류, 내부 경로, 라이브러리 예외 메시지. 사용자에게는 일반 메시지와 추적용 식별자만 준다. 예외 객체를 문자열로 만들어 응답에 넣으면 상위 요청의 인증 헤더까지 새어 나갈 수 있다.
- **클라이언트가 잘못 보낸 요청(깨진 본문, 지원 안 하는 형식, 타입 불일치)은 4xx로 분류한다**(1-18). catch-all 예외 처리만 두면 이런 것도 500과 함께 서버 오류로 로그에 잡혀, 인증 없이도 반복 호출로 로그를 부풀릴 수 있다.
- **요청 파이프라인 앞단(필터·미들웨어)에서 오류를 직접 응답해야 한다면, 프레임워크의 표준 오류 라우팅(에러 페이지 전달·재진입)을 우회할지부터 확인한다**(1-19). 표준 경로를 타면 그 오류 응답이 인증·인가 같은 뒷단 컴포넌트를 다시 통과하면서 상태(상태 코드 등)가 뒤바뀔 수 있다.
- 인증·인가 실패, 권한 변경 같은 보안 사건은 **추적 가능하게** 기록한다.
- **오류 경로를 비워두지 않는다.** 실패할 수 있는 모든 호출에 대응을 정의한다. 반환값·상태 코드를 확인하지 않고 성공을 가정하지 않는다.
- **예외를 삼키지 않는다.** 비어 있는 예외 처리, 모든 예외를 한 덩어리로 잡아 무시하는 처리, 실패했는데 정상 응답을 돌려주는 처리를 만들지 않는다.
- **실패했을 때 안전한 쪽으로 떨어지게** 한다 — 오류가 나면 접근을 허용하는 형태(예: 권한 조회 실패 시 통과)를 만들지 않는다.

## 12. 시간과 상태

> **이 렌즈로 보라: "같은 요청이 동시에 두 번 들어오면?"** 기능이 동작하는 것을 확인했더라도 이 질문을 따로 던진다. 순차 실행만 상정한 코드는 테스트를 통과한다.

- **검사 시점과 사용 시점이 벌어지지 않게** 한다. "존재 확인 → 열기", "잔액 확인 → 차감", "권한 확인 → 실행" 사이에 상태가 바뀔 수 있다. **원자적 연산·잠금·트랜잭션·조건부 갱신**으로 묶는다.
- 조건부 갱신의 형태: `UPDATE ... SET p = p - ? WHERE id = ? AND p >= ?`, `UPDATE ... SET n = n + 1 WHERE n < ?`, 유니크 제약을 이용한 선점. 애플리케이션 잠금보다 먼저 고려한다.
- **조건부 갱신을 여러 번 이어 붙인 것은 트랜잭션이 아니다.** 실패 시 수동 보상(환불·해제)을 넣는 구조는 보상 코드가 실행될 때까지 프로세스가 살아 있어야 성립한다. 차감과 지급, 예약과 확정처럼 짝을 이루는 연산은 트랜잭션으로 묶는다 (**1-6**).
- **같은 요청이 동시에 여러 번 들어오는 상황**을 가정한다 — 쿠폰 중복 사용, 중복 결제, 재고 음수는 대개 여기서 나온다.
- 공유 자원을 다루는 코드에 **동시성 통제**를 둔다. 요청 처리 중 전역·정적 상태에 값을 보관하지 않는다.
- **반복·재귀에 종료 조건과 상한**을 둔다. 외부 입력이 반복 횟수·깊이를 결정하게 하지 않는다.

## 13. 자원과 메모리

> **이 렌즈로 보라: "이 값이 최댓값이면? 음수면? 이 호출이 실패하면?"** 언어에 따라 해당 범위가 다르다. 메모리를 직접 다루는 언어에서는 전부, 관리형 언어에서는 상한·해제·초기화 항목이 해당된다.

- **상한 검사를 자원을 쓰기 전에 한다.** 전부 읽고 전부 파싱한 뒤 개수를 세면 이미 늦다. 프레임워크의 요청 크기 상한은 원본 바이트만 막을 뿐, 파싱 후 객체가 몇 배로 부푸는 것은 막지 못한다. 가능하면 스트리밍으로 처리하고, 아니면 읽는 중 누적 검사한다 (**1-3**).
- **곱셈·덧셈에서 넘치는지 확인한다.** 두 값을 각각 검사해도 `page * size` 같은 계산이 넘쳐 음수가 되면 경계 검사가 무력화된다. 넓은 타입으로 계산하거나 결과에 상한을 건다 (**1-4**).
- **캐시에 크기 상한과 만료를 둔다.** 키가 외부 입력이면 항목 수에 상한이 없다. 캐시에 담기는 객체에 자격증명·개인정보 필드가 섞여 있으면 그것을 무기한 메모리에 상주시키는 셈이다 (**1-5**).
- **자원을 확실히 해제한다** — 파일·연결·잠금·핸들. 예외 경로에서도 해제되게 언어의 자동 해제 구문을 쓴다. 해제한 자원을 다시 쓰거나 두 번 해제하지 않는다.
- **경계를 넘지 않는다** — 버퍼 크기를 확인하고, 길이 계산에 외부 입력을 그대로 쓰지 않는다.
- **정수 연산의 범위를 확인한다** — 크기·개수·오프셋 계산에서 넘침·음수가 생기면 경계 검사가 무력화된다.
- **형식 문자열에 외부 입력을 넣지 않는다.** 형식은 고정하고 값만 인자로 전달한다.
- **참조 사용 전 유효성을 확인한다** — 반환값이 없을 수 있는 호출의 결과를 확인 없이 사용하지 않는다.
- **초기화 전에 사용하지 않는다.**

## 14. 캡슐화

> **이 렌즈로 보라: "이 값이 다른 사용자의 요청에서도 보이는가?"**

- **요청 데이터를 공유 영역에 보관하지 않는다** — 전역·정적·싱글톤에 사용자별 값을 담으면 **다른 사용자에게 노출**된다. 대부분의 프레임워크에서 컨트롤러·서비스 빈은 기본이 싱글톤이다.
- **디버그·시험용 코드를 남기지 않는다** — 인증을 건너뛰는 분기, 시험용 계정, 내부 정보를 출력하는 엔드포인트, 주석 처리된 검증 로직.
- **내부 자료구조를 그대로 주고받지 않는다** — 내부 배열·컬렉션의 참조를 외부에 반환하거나 외부 참조를 그대로 보관하면, 바깥에서 내부 상태를 바꿀 수 있다. 복사해서 전달한다. 캐시가 반환하는 컬렉션도 여러 요청이 공유한다.
- 공유 자료구조는 스레드 안전한 것을 쓴다.

## 15. API 사용

- **이름 조회 결과로 보안을 판단하지 않는다** — 도메인 이름·역방향 조회 결과는 위조될 수 있다. 인증·인가 판단의 근거로 쓰지 않는다.
- **폐기·비권장 API 를 쓰지 않는다.** 문서에서 대체 API 를 확인하고, 안전한 변형이 있으면 그것을 쓴다.
- **API 의 보안 관련 기본값을 확인한다** — 검증·이스케이프·타임아웃이 기본으로 켜져 있는지 확인하고, 꺼져 있으면 명시적으로 켠다.
- **하위 프로세스·에이전트를 권한 우회 모드로 실행하지 않는다.** 격리 경계나 명령 분류기가 없는 상태에서 임의 명령 실행을 허용하지 않는다.
- **권한 부여는 목적에 맞게 좁힌다** — 읽기만 필요한데 쓰기 권한, 리소스 하나면 되는데 프로젝트 전체, 세분화된 역할이 있는데 상위 역할. 신뢰 정책의 조건이 의도보다 넓은 주체를 받아들이는지 확인한다.
- **기능을 하나 더할 때마다 권한이 함께 넓어진다.** 새 기능 하나 때문에 올린 스코프·역할은 **앱 전체에 적용된다** — 그 기능만 좁은 권한으로 할 수 있는지 먼저 확인하고, 없으면 왜 넓혀야 했는지를 남긴다. 기능이 적을 때는 좁았는데 늘면서 넓어진 것을 **아무도 되돌리지 않는다.** 선언된 권한 목록을 기능 목록과 나란히 놓고, 지금도 필요한지 확인한다.
