# app-diagnosis

운영 중인 애플리케이션이 Terroir 로 들어올 수 있는지, BYOR 과 greenfield 중 어느 경로인지 가릴 수 있게 현황을 정리한다.

## 무엇을 하는가

운영 중인 앱을 Terroir 로 옮기려면 먼저 **들어올 수 있는지, 어떤 경로인지**를 가려야 한다. 앱을 만든 사람은 그 판단에
무엇이 필요한지 모르는 경우가 많아서, 이 스킬이 **같은 목차의 진단 문서**를 만든다.

문서 맨 위에서 판단에 필요한 것을 먼저 보여 준다.

| 맨 위 | 담는 것 |
|---|---|
| 사전 체크 | 프로젝트 정보 · 실행 계정명 · 조직 소속 여부 · Terroir 플러그인 설치 여부와 버전 · 도커라이징 여부 |
| 이관 경로 판단 | BYOR · greenfield · 확인 필요 중 1차 의견과 근거. 소스 위치, 컨테이너 실행, 앱 형태, 플랫폼 종속 |

그 아래는 판단의 근거와 이관 준비에 필요한 정보다.

| 목차 | 담는 것 |
|---|---|
| 1 기술 스택 | 언어, 프레임워크, 런타임, 주요 라이브러리 |
| 2 아키텍처 | 외부 리소스와 DB 를 넣은 구조도, 서버 로직의 위치 |
| 3 앱 구조와 실행 형태 | 저장소 구조, 빌드·시작 명령, 포트, 상태 저장 위치, 업로드 방식, 예약 작업, 헬스체크 |
| 4 도커라이징 | 앱이 몇 개인지, 앱마다 Dockerfile 이 있는지, 없으면 만들 수 있는지 |
| 5 배포 파이프라인 | 자동 · 수동 · 없음, 이미지 저장 위치, 비밀값 주입, 환경별 배포 대상 |
| 6 외부 리소스 | 리소스마다 용도·식별 정보·설정 위치·소유 계정 |
| 7 운영 현황 | DB 공유, 마이그레이션, 사용량, 서버 사양 |
| 8 주소와 저장소 | 현재 URL 과 그 URL 이 등록된 곳, 저장소 소유와 공개 여부 |

확인하지 못한 항목은 「알 수 없음」 과 문의처로 남는다. 비밀값은 이름과 위치만 적는다.

실행하면 먼저 **직접 진단할지, 담당자에게 전달할지** 묻는다.

| 고른 것 | 결과 |
|---|---|
| 직접 진단 | 로컬 경로나 원격 저장소 주소를 받아 진단하고 아티팩트 링크를 준다 |
| 담당자에게 전달 | 담당자에게 보낼 짧은 메시지를 출력한다. 담당자는 그 안의 지시를 자기 Claude Code 에 붙여 넣는다. 이 플러그인은 없어도 된다 |

두 경로는 같은 지시(`references/format.md`)와 같은 틀(`references/report-template.html`)을 쓴다. 조사 순서와 판단 규칙은 틀의 머리 주석에 있다.

## 결과 모양

결과는 디자인이 고정된 리포트 한 장이다. 맨 위에 이관 경로 1차 의견과 근거, 사전 체크, 먼저 볼 신호가 있고 그 아래에 1~8 절이 있다.

- 샘플: https://claude.ai/artifact/LTgr9xsL3wJ3WV7q4K61QN — V.Together 를 진단한 예시
- 틀: `skills/app-diagnosis/references/report-template.html` — 조사 안내 · 판단 규칙 · 디자인의 원본. 진단 데이터는 JSON 칸에만 들어간다

전달 경로로 받은 담당자의 AI 는 틀의 GitHub 공개 주소를 읽어 같은 모양으로 만든다. 주소를 읽지 못하면 진행하지 않고 그렇다고 답한다.

## 쓰는 법

```
/plugin install app-diagnosis@terroir-community-plugin
/app-diagnosis:app-diagnosis
```

"현황 진단해줘", "담당자한테 보낼 진단 요청 만들어줘" 같은 말에도 실행된다.

## 전제 조건

| | |
|---|---|
| 외부 도구 | `git` — 원격 저장소 주소로 진단할 때만 |
| 접근 권한 | 진단할 저장소를 읽을 권한. 클라우드 설정까지 보려면 그 클라우드 프로젝트의 읽기 권한. 없으면 해당 항목이 「알 수 없음」 이 된다 |
| 다른 플러그인 | 없음 |

## 아는 한계

- **이관 경로는 1차 의견이다.** 공개된 두 경로의 기준으로만 가른다. 사내 표준의 세부 대조와 최종 결정은 결과를 받은 쪽이 한다
- **Dockerfile 을 만들지 않는다.** 만들 수 있는지만 판단한다
- **코드에 없는 것은 사람이 답해야 한다.** 사용자 수, 접속 환경, 트래픽은 묻거나 모니터링 화면 위치만 남긴다
- **링크로 주려면 세션에 아티팩트나 문서를 만드는 도구가 있어야 한다.** 없으면 마크다운 파일로 저장한다
- 원격 주소로 진단하면 커밋하지 않은 변경과 로컬 `.env` 를 볼 수 없다
- 전달한 메시지의 결과 깊이는 받는 사람의 Claude 환경에 따라 다르다. 소스 코드를 읽을 수 없는 환경이면 「알 수 없음」 이 늘어난다
- 전달 경로의 틀 주소는 `main` 브랜치를 가리킨다. 틀을 고친 PR 이 머지되기 전에는 담당자가 이전 틀을 받고, 처음 머지되기 전에는 틀을 받지 못한다
- 샘플 아티팩트는 공유된 사람만 열 수 있다. 열리지 않아도 틀 주소만 읽히면 같은 모양으로 만들어진다

## 틀을 고칠 때

**`report-template.html` 이 원본이고, 샘플 아티팩트는 그 사본이다.** 틀을 고치면 같은 PR 에서 아래를 함께 한다.

1. 틀 안 `TEMPLATE_VERSION` 과 `plugin.json` 의 `version` 을 올린다. 샘플 화면 맨 아래에 틀 버전이 보인다
2. 고친 틀 파일을 샘플 아티팩트 주소에 그대로 다시 게시한다. Claude Code 에서 「이 파일로 샘플 아티팩트 다시 게시해줘」 라고 하면 된다
3. 샘플 화면 맨 아래의 틀 버전이 새 버전인지 확인한다

샘플 아티팩트의 게시는 소유자 계정으로만 할 수 있다. CI 가 이 둘을 맞춰 주지 않는다.
