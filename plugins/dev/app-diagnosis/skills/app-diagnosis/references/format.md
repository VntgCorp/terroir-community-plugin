# 앱 이관 현황 진단 : <앱 이름>

이 앱을 사내 개발 플랫폼 Terroir 로 옮기려고 한다.
**이 진단의 목적은 이 앱이 Terroir 로 들어올 수 있는지, 들어온다면 BYOR 과 greenfield 중 어느 경로인지 가리는 것이다.**
그 판단에 필요한 기술 스택·아키텍처·앱 구조·도커라이징·배포 파이프라인을 중심으로 조사해 아티팩트 한 개로 정리한다.
결과 문서의 제목은 「앱 이관 현황 진단 : <앱 이름>」 으로 한다.

## 지킬 것

- 결과와 마지막 응답은 한국어로 쓴다.
- 코드·설정 파일·조회 결과에서 확인한 것만 적는다. 근거가 된 파일 경로를 함께 적는다.
- 확인하지 못한 항목은 「알 수 없음」으로 쓰고, 누구에게 물으면 알 수 있는지 함께 적는다. 추측으로 채우지 않는다.
- 비밀번호·키·토큰의 값은 적지 않는다. 이름과 보관 위치만 적는다. `.env` 같은 파일은 키 이름만 본다.
- 클라우드 콘솔이나 CLI 로 조회할 때는 읽기 명령만 쓴다. 아무것도 만들거나 바꾸지 않는다.
- 소스 코드를 고치지 않는다. Dockerfile 이 없어도 새로 만들지 않는다.
- Terroir 에서 무엇으로 바꿀지는 제안하지 않는다. 지금 어떻게 되어 있는지만 적는다. 바꿀 방법은 Terroir 표준을 아는 쪽이 정한다.

## 사전 체크

표 하나로 적는다.

| 항목 | 적을 것 |
|---|---|
| 프로젝트 정보 | 앱 이름 · 한 줄 설명 · 소스 위치(저장소 주소 또는 폴더) |
| 실행 계정명 | 이 진단을 실행한 사람의 GitHub 계정 이름 |
| 조직 소속 여부 | 그 계정이 GitHub VntgCorp 조직에 속해 있는지 |
| Terroir 플러그인 설치 여부 | 이 Claude 에 설치된 Terroir 플러그인 이름과 버전. 없으면 「없음」 |
| 도커라이징 여부 | 「됨」 · 「가능」 · 「어려움」 중 하나와 한 줄 근거. 자세한 내용은 4절 |

## 이관 경로 판단

**1차 의견**을 「BYOR」 · 「greenfield」 · 「확인 필요」 중 하나로 적고, 아래 네 가지 근거를 표로 붙인다.
최종 결정은 결과를 받은 쪽이 한다.

| 근거 | 확인할 것 |
|---|---|
| 소스 위치 | 소스 코드가 git 저장소에 있는가. 개인 계정인가, 조직인가 |
| 컨테이너 실행 | 컨테이너 이미지로 만들어 실행할 수 있는가. 4절의 결론 |
| 앱 형태 | HTTP 요청을 받는 서버인가, 정적 화면인가, 정해진 시간에 도는 작업인가. 하나의 앱인가, 여러 앱이 한 저장소에 있는가 |
| 플랫폼 종속 | 특정 서비스 안에서만 돌아가는가. 예: Google Apps Script, 노코드 도구, 서버리스 함수 전용 코드. 서버의 호스트 권한이나 파일 시스템을 직접 써야 하는가 |

두 경로의 뜻은 이렇다. 판단에만 쓰고 결과에 옮겨 적지 않는다.

- **BYOR** — 이미 있는 저장소에 Terroir 표준 파일을 얹어 그대로 옮긴다. git 저장소가 있고 컨테이너로 실행할 수 있어야 한다. 저장소는 VntgCorp 조직으로 옮겨야 한다
- **greenfield** — Terroir 가 새 저장소를 만들어 주고, 기존 기능을 그 안에 다시 옮겨 담는다. 소스가 git 저장소에 없거나, 특정 서비스에 묶여 컨테이너로 실행할 수 없을 때다

## 목차

### 1. 기술 스택

- 언어, 프레임워크, 런타임 버전, 패키지 관리 도구
- 주요 라이브러리: 화면, 데이터 접근, 인증, 외부 연동
- 테스트와 린트 도구가 있는지

### 2. 아키텍처

- 화면·서버·DB·외부 서비스가 어떻게 연결되는지 그림 한 장. 외부 리소스 이름과 DB 를 그림에 넣는다
- 서버 로직이 어디서 도는지: 별도 백엔드, 프레임워크의 서버 기능, 브라우저에서 DB 에 직접 접속 등
- DB: 종류, 주요 테이블, 스키마와 마이그레이션 파일 위치

### 3. 앱 구조와 실행 형태

- 저장소 구조: 앱 하나인지 여러 개인지, 주요 디렉토리와 역할
- 실행 방법: 빌드 명령, 시작 명령, 앱이 받는 포트
- 상태를 어디에 두는지: 서버 로컬 디스크에 파일이나 세션을 저장하는지, 외부 저장소에 두는지
- 파일 업로드 방식: 브라우저에서 저장소로 바로 올리는지, 서버가 multipart 폼으로 받는지. 서버가 받으면 그 코드의 파일 경로
- 정해진 시간에 도는 작업: 무엇을, 얼마나 자주, 무엇이 호출하는지
- 로그인 없이 200 을 돌려주는 헬스체크 주소가 있는지

### 4. 도커라이징

Dockerfile 의 내용이 아니라 **앱마다 컨테이너로 만들 수 있는지**를 본다.

먼저 저장소에 배포 단위가 되는 앱이 몇 개인지 센다. 서버, 화면, 정해진 시간에 도는 작업이 따로 실행되면 각각 하나로 센다.
같은 앱 안의 API 경로나 보조 스크립트는 따로 세지 않는다.

앱마다 표 한 줄로 적는다: 앱 이름과 경로 · 역할 · Dockerfile 유무와 경로 · Dockerfile 이 없으면 도커라이징 가능 여부와 근거

- **가능** 의 근거: 런타임과 빌드·시작 명령이 분명하다
- **어려움** 의 근거: 특정 서비스 안에서만 돈다, 호스트 권한이나 서버 파일 시스템이 필요하다, 시작 명령을 알 수 없다

마지막에 전체 결론을 「됨」 · 「가능」 · 「어려움」 중 하나로 적는다. 모든 앱에 Dockerfile 이 있으면 「됨」, 없는 앱이 있지만 모두 만들 수 있으면 「가능」, 하나라도 어려우면 「어려움」 이다.

### 5. 배포 파이프라인

결론을 「자동」 · 「수동」 · 「없음」 중 하나로 먼저 적는다.

- **자동** — CI/CD 설정 파일의 위치와 무엇이 배포를 시작하는지. 예: 브랜치 push, 태그
- **수동** — 누가 어떤 명령이나 스크립트로 배포하는지
- **없음** — 배포 스크립트도 기록도 찾지 못했다

어느 쪽이든 아래를 함께 적는다.

- 이미지나 빌드 결과물을 어디에 저장하는지
- 환경변수와 비밀값을 앱에 넣는 방식
- 환경마다 어디로 배포되는지. 운영과 개발이 나뉘어 있는지

### 6. 외부 리소스

리소스마다 표 한 줄로 적는다: 이름 · 용도 · 식별 정보(프로젝트 ID, 주소 등) · 설정 위치(파일, 환경변수 이름) · 소유 계정

- 개인 계정에 묶인 것은 따로 표시한다
- 코드에서 쓰지 않는데 설정에만 남은 키도 적는다

### 7. 운영 현황

- 운영 환경과 개발 환경이 같은 DB 를 함께 쓰는지
- DB 마이그레이션을 어떻게 적용하는지. 적용 이력이 남는지
- 사용자 규모, 사무실 밖이나 휴대폰 접속 여부
- 하루 요청 수와 사용량이 몰리는 시기. 수치가 없으면 볼 수 있는 모니터링 화면의 이름과 위치
- 현재 서버 사양: CPU, 메모리, 인스턴스 수, 자동 확장 설정

### 8. 주소와 저장소

- 현재 서비스 URL 과 커스텀 도메인
- 이 URL 이 등록된 곳: 로그인 Redirect URL, OAuth 설정, 메일 본문 링크, 분석 도구, 공지·북마크
- 저장소의 소유, 공개 여부, 브랜치, 커밋하지 않은 변경

## 결과 형식

결과는 **리포트 틀에 진단 데이터를 채운 HTML 한 개**다. 모양은 아래 샘플과 같아야 한다.

- 샘플 화면: https://claude.ai/artifact/LTgr9xsL3wJ3WV7q4K61QN
  사람이 모양을 볼 때 쓴다. 열리지 않으면 건너뛴다
- 리포트 틀: https://raw.githubusercontent.com/VntgCorp/terroir-community-plugin/main/plugins/dev/app-diagnosis/skills/app-diagnosis/references/report-template.html
  이 파일을 받아서 채운다. 플러그인으로 실행 중이면 스킬의 `references/report-template.html` 을 읽는다

1. 틀 파일을 받는다.
2. 틀 안에 든 V.Together 예시 JSON 과 **같은 칸 이름**으로 진단 결과를 쓴다.
   - 사전 체크 → `precheck` · 이관 경로 판단 → `path` · 1~8 절 → `sections` · 「알 수 없음」 모음 → `unknowns`
   - `signals` 에는 코드에서 확인한 걸림돌을 사실로만 적는다. 예: 헬스체크 주소 없음, 수동 배포
   - `sample` 칸은 지운다
3. 틀 머리 주석의 「채우는 법」 을 따른다. JSON 칸과 `<title>` 의 앱 이름만 바꾸고 다른 줄은 고치지 않는다.
4. 그 HTML 을 아티팩트로 만들어 링크를 공유한다. 아티팩트를 만들 수 없으면 맨 앞에 `<!doctype html>` 한 줄을 붙여 `.html` 파일로 저장한다.
5. 틀 파일을 받지 못하면 같은 순서의 마크다운 한 개로 정리한다: 사전 체크 · 이관 경로 판단 · 1~8 절 · 「알 수 없음」 모음
