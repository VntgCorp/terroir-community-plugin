# 페이지 글쓰기 규칙

리뷰 페이지는 팀원 · 팀장 · 옆 팀이 회의 중에 한 번 훑어보고 판단하는 문서다. 이 페이지 하나만 읽고
이해되어야 한다.

## 다른 문서를 알아야 읽히는 표현을 쓰지 않는다

점검표 항목 번호 · 결정 문서 번호 · PR 번호 · 규칙 번호 · 설정 키 이름은 쓴 사람만 안다. 무엇을 확인했고
무엇이 문제였는지 풀어 쓴다.

| 피할 표현 | 대신 쓸 표현 |
|---|---|
| IAM 정리 (1-1 · 1-2 예외) | 안 쓰는 계정 정리. 팀 업무에 필요한 개인 권한 몇 건은 이유를 적어 예외로 둠 |
| 규칙 942550 오탐 | 정상 저장 요청이 공격으로 잘못 판정돼 막힘 |
| viewers_can_edit 끔 | 보기 권한 사용자의 편집 허용 설정을 끔 |
| PR #1810 에 쌓음 | 변경을 만들어 리뷰를 기다림 |

티켓 키는 링크로만 두고 옆에 내용을 알 수 있는 이름을 붙인다.

## 전제가 되는 말은 맨 위에서 푼다

「점검」 「감사」 「이관」처럼 페이지 전체가 기대는 말은 머리의 용어 풀이 상자(`dl.terms`)에 한 줄씩 적는다.
언제 · 누가 · 무엇을 한 것인지까지 적는다.

## 결론을 먼저 쓴다

- 머리의 결론 블록이 페이지의 답이다. 다섯 가지를 위에서부터 둔다
  - **한 문장 결론** — 이번 스프린트를 한 줄로. 잘된 쪽은 `strong`, 문제 쪽은 `em`
  - **숫자 셋** — 끝낸 티켓, 계획한 티켓의 실제 / 추정, 추정 없이 들어온 일
  - **2주를 어디에 썼나** — 일할 수 있던 날 전체를 일의 종류로 나눈 막대 하나
  - **회고 세 칸** — 잘된 것 · 아쉬운 것 · 다음엔. 칸마다 2~3줄
  - **다음 스프린트 한 줄** — 일할 수 있는 날, 추정 합, 넘칠 것
- 각 섹션의 첫 문장이 그 섹션의 결론이다. 근거는 그 밑의 카드 · 표 · 막대가 보여 준다
- 긴 설명(티켓별 설명 · 계산 방법)은 펼침 상자(`details`)에 담는다

## 숫자

- 단위를 붙인다 (`0.5일` · `3건`). 소수 첫째 자리까지
- 근사치는 근사치라고 적고 구한 방법을 펼침 상자에 남긴다
- 막대 길이는 같은 표 안에서 같은 기준으로 계산한다. 기준은 템플릿 주석에 있다

## 사람

- 사람별 생산성 · 완료 수로 줄 세우지 않는다. 팀 범위 보고서도 묶음 · 티켓 단위로 쓴다
- 다른 사람이 한 일(취소 · 결정)을 적을 때는 이름보다 이유를 적는다

## 민감한 내용

보안 취약점의 상세(어디가 어떻게 뚫리는지), 고객 정보, 계정 · 토큰은 페이지에 적지 않는다.
필요하면 「보안 점검 지적 4건 조치」처럼 범위만 적는다. 이미 적었다면 공유 범위를 사용자에게 확인한다.

## 문장

- 짧게 쓴다. 한 문장에 한 가지
- 같은 블록 안에서는 종결을 맞춘다. 문단은 「~습니다」, 표 칸과 목록은 「~함 · ~음」 같은 명사형
- 연결어미(-고 · -며 · -지만) 뒤에 쉼표를 찍지 않는다
- 「핵심」 「중요」 같은 평가어 대신 수치와 사실을 쓴다
- 비유하지 않는다. 「막혔다」 「넘쳤다」처럼 일어난 일을 그대로 쓴다

## 섹션 이름

템플릿의 섹션 이름을 그대로 쓴다. 매 스프린트 같은 자리에 같은 이름이 있어야 지난 페이지와 나란히 놓고 비교할 수 있다.
