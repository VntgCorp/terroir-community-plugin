# 스프린트 리뷰 · 플래닝 보고서

지난 스프린트에서 한 일, 계획이 맞은 정도, 다음 스프린트에 들어갈 일을 한 장짜리 페이지로 만든다.
모양은 `assets/template.html` 을 그대로 쓴다.

팀마다 스프린트 길이 · 경계 시각 · 추정 단위 · 작업 시간 기록 방식이 다르다. 그래서 처음 쓰는
팀이면 이것부터 묻고 **팀 설정 파일**로 저장한다. 두 번째부터는 저장한 설정을 읽고 바로 시작한다.

## 이 스킬에 든 것

| 파일 | 언제 읽나 |
|---|---|
| `references/setup.md` | 팀 설정 파일이 없을 때 · 사용자가 설정을 바꾸자고 할 때. 묻는 항목과 저장 형식 |
| `references/data.md` | 티켓 · 추정 · 실제 시간 · 일할 수 있는 날을 모을 때. 계산 규칙 |
| `references/writing.md` | 페이지 글을 쓸 때. 다른 사람이 이 페이지 하나로 이해하게 쓰는 규칙 |
| `assets/template.html` | 페이지를 만들 때. 가상의 예시 팀 데이터가 들어 있고 구조 · 클래스 · 순서를 그대로 쓴다 |

## 절차

### 0. 팀 설정을 불러온다

`~/.claude/sprint-review/` 의 설정 파일(`<팀이름>.md`)을 찾는다.

- **하나 있으면** 그 파일을 읽고 사용자에게 한 줄로 알린다. 예 「예시 개발팀 설정(2주 · 목요일 15:00 경계 · 추정 일 단위)으로 만듭니다」
- **여러 개면** 어느 팀인지 묻는다
- **없으면** `references/setup.md` 를 읽고 그 순서대로 묻는다. 다 물으면 설정 파일을 저장하고 내용을 보여 준다

사용자가 대화 중에 설정과 다른 사실을 알려 주면(예 「우리는 목요일 오후 3시가 경계야」) 이번 보고서에
반영한다. 끝날 때 설정 파일에도 고칠지 한 번 묻는다.

### 1. 두 스프린트의 기간을 정한다

설정의 경계 규칙으로 **지난 스프린트**(리뷰 대상)와 **다음 스프린트**(플래닝 대상)의 시작 · 끝 시각을
구한다. 이슈 트래커의 스프린트 시작 · 종료 시각이 팀의 실제 경계와 다를 수 있다. 다르면 팀 설정이 맞다.

예 — 경계가 「2주마다 목요일 15:00」이면 오늘이 목요일 리뷰 날일 때 지난 스프린트는 2주 전 목요일
15:00 부터 오늘 15:00 까지, 다음 스프린트는 오늘 15:00 부터 2주 뒤 목요일 15:00 까지다. 경계 날 오전은
이전 스프린트로 친다.

### 2. 데이터를 모은다

`references/data.md` 를 읽고 그대로 모은다. 모을 것은 다섯 가지다.

1. 두 스프린트의 티켓 목록과 상태 · 담당자 · 상위 묶음
2. 티켓마다 계획 때 넣은 추정
3. 티켓마다 실제로 쓴 시간 (작업 시간 기록 또는 활동 기반 근사)
4. 캘린더에서 빠지는 시간 (휴가 · 종일 행사 · 긴 회의)
5. 지난 리뷰 페이지가 있으면 그때 세운 계획과 목표

도구가 연결돼 있지 않으면 멈추지 말고 사용자에게 그 부분만 붙여 넣어 달라고 한다.
예 「Jira 가 연결돼 있지 않습니다. 지난 스프린트 티켓 목록(키 · 제목 · 상태 · 추정)을 붙여 넣어 주세요」

### 3. 분류하고 계산한다

`references/data.md` 의 규칙대로 다섯 가지를 구한다.

- 티켓을 세 묶음으로 나눈다 — **① 처음 계획한 티켓**, **② 처음부터 있었지만 추정이 없던 일**, **③ 중간에 들어온 일**
- 일할 수 있던 날 · 일할 수 있는 날 (두 스프린트 모두)
- 묶음별 · 티켓별 추정과 실제, 그 차이의 이유
- 다음 스프린트 티켓을 급한 순서로 쌓았을 때 어디까지 들어가는지
- 일할 수 있던 날을 일의 종류로 나눈 「2주를 어디에 썼나」 칸

숫자는 소수 첫째 자리까지 쓰고 근사치는 근사치라고 적는다. 반올림 때문에 합이 0.1 어긋나는 것은 괜찮다.

### 4. 페이지를 만든다

`assets/template.html` 을 복사해 값을 채운다. `references/writing.md` 의 규칙을 지킨다.

- 섹션 순서는 템플릿과 같다 — 결론 블록 → 지난 스프린트 → 끝낸 날 → 추정과 실제 → 대표 작업 전후(선택) → 다음 스프린트
- 결론 블록만 읽고도 「이번 스프린트가 어땠나」에 답할 수 있어야 한다. 그 아래 섹션은 근거 자료다
- 막대 너비 · 누적 위치는 템플릿 주석의 계산식으로 다시 계산한다. 예시 값을 그대로 두지 않는다
- 데이터가 없는 블록은 비워 두지 말고 블록째 뺀다 (예 대표 작업이 없으면 그 섹션을 뺀다)

### 5. 공유한다

설정의 공유 방식을 따른다.

- **claude.ai 아티팩트** — Artifact 도구가 있으면 게시하고 링크를 준다. 지난 리뷰 페이지와 다른 새 페이지로 만든다
- **HTML 파일** — 사용자가 정한 위치에 저장하고 경로를 준다

마지막 답변에 네 가지를 짧게 적는다.

- 일할 수 있는 날과 그 계산에서 뺀 일정
- 실제 시간이 근사치이면 어떻게 구했는지 한 줄
- 사용자가 확인해야 할 판단 (예 다음 스프린트에서 어디서 끊을지 제안한 것)
- 공유 범위 — 보안 취약점 상세 같은 민감한 내용이 있으면 누구에게 보여 줄지 확인하라고 알린다

## 하지 않는 것

- 다음 스프린트 범위를 정하지 않는다. 어디까지 들어가는지 보여 주고 어디서 끊을지는 **제안**만 한다
- 이슈 트래커의 티켓 · 스프린트 · 추정 값을 고치지 않는다. 읽기만 한다
- 사람별 생산성을 비교하지 않는다. 팀 범위 보고서라도 사람을 줄 세우는 표를 만들지 않는다
