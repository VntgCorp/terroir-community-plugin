# 한국어 기술 문서 작성

문체와 용어를 내가 만들지 않는다. 그 주제를 다루는 대기업 공개 문서를 실제로 열어
거기 쓰인 단어와 문장 형태를 가져온다. 검증된 표현이기 때문이다.
문서를 어떤 유형으로 어떤 순서로 짤지는 토스 테크니컬 라이팅 가이드(technical-writing.dev)를 따른다.

**이 스킬은 쓰기 전에 돈다.** 다 쓰고 나서 고치는 것보다 효과가 크다. 한 사내 문서를 이 절차로
다시 쓰자 검사 결과가 21건(용어 20 + 종결어미 혼용 경어체 25 대 해라체 61)에서 0건이 됐다.

## 이 스킬에 든 것

| 파일 | 하는 일 |
|---|---|
| `ko-style/` | 용어집 초기본. 처음 실행할 때 `~/.claude/ko-style/` 로 복사하고 그 뒤로는 거기에 쌓는다 |
| `scripts/init-style.py` | 초기본에서 사용자 용어집에 없는 파일만 복사한다 |
| `references/doc-types.md` | 문서 유형별 템플릿·체크리스트 |
| `scripts/structure-check.py` | 다 쓴 문서의 목차 구조 점검 |
| `scripts/ko-lint.py` | 용어집과 문장 규칙으로 문서를 검사한다. 이미 아는 금지 표현만 잡는다 |

`ko-lint.py` 는 처음 보는 개념을 뭐라고 부를지, 문서를 어떤 순서로 짤지는 알려주지 않는다.
이 스킬이 쓰기 전에 그 둘을 정한다 — 유형과 목차를 먼저 세우고 표준 표현을 구해 온다.

## 절차

### 0. 대상과 독자를 정한다

무엇을 쓰는지, 읽는 사람이 누구이고 무엇을 이미 아는지 확인한다. 사용자 가이드·TechDocs·README 는 경어체다.
내부 ADR·메모리·설계 노트는 해라체 그대로 쓰고 이 스킬을 돌리지 않는다.

### 1. 문서 유형을 정한다

독자가 이 문서를 여는 목적이 유형을 정한다. 한 페이지의 주된 유형은 하나다.

| 유형 | 독자가 여는 때 | 하위 형태 |
|---|---|---|
| 학습 | 처음 접해서 흐름을 익히고 싶을 때 | 시작하기 · 튜토리얼 |
| 문제 해결 | 특정 작업을 하거나 특정 문제를 풀고 싶을 때 | How-to 가이드 · 트러블슈팅 |
| 참조 | 특정 기능·API 의 세부 사항을 찾을 때 | API 레퍼런스 · 에러 코드 목록 |
| 설명 | 개념·원리·배경을 이해하고 싶을 때 | 개념 문서 · 도메인 문서 |

`references/doc-types.md` 를 읽고 그 유형의 템플릿과 체크리스트로 시작한다.
How-to 와 참조가 둘 다 필요하면 페이지를 나누고 서로 링크한다. 문서 묶음을 새로
만들면 같은 파일의 「여러 페이지 문서의 구조」를 따른다.

### 2. 목차를 먼저 짠다

본문보다 제목 목록을 먼저 쓰고 아래를 맞춘다.

- **한 페이지에서 하나만 다룬다.** 제목이 H4 까지 내려가면 하위 개념을 별도 문서로 나눌지 본다.
  핵심 주제가 둘이면 나누고, 여러 개념을 개략적으로 소개해야 하면 개요 페이지를 따로 만들어 링크한다
- **첫 제목 바로 아래에 개요를 둔다.** 「이 문서를 읽으면 무엇을 할 수 있는가」에 답하는 한두 문장이다.
  기술 배경부터 쓰지 않는다
- **독자가 얻는 것을 먼저 쓴다.** 도입·기능 역사·옵션 나열은 뒤로 보낸다.
  `이 API는 여러 설정 옵션을 제공합니다` 가 아니라 `이 API를 사용하면 로그 데이터를 실시간으로 처리할 수 있습니다`
- **제목** — 핵심 키워드를 넣고(`에러를 해결하는 방법` → `NOT_FOUND_USER 에러를 해결하는 방법`)
  30자 이내 평서문으로 쓴다. 같은 수준의 제목은 같은 형태로 맞춘다 — 명사구 기본, `~하기` 도 되지만
  한 문서 안에서 섞지 않는다. 단계를 다루면 `1단계. 프로젝트 설정하기` 처럼 번호를 붙인다
- **순서** — 핵심 개념 → 사용법 → 예제 → 심화. 코드 앞에 그 코드가 무엇을 하는지 한 문장 먼저 쓴다
- **같은 내용은 같은 절 이름** — 한 문서에서 `설치`, 다른 문서에서 `환경 설정` 으로 부르지 않는다
- **새 개념은 처음 나온 자리에서 한두 문장으로 정의한다.** 필드·설정값은 어떤 조건에서
  어떻게 동작하는지, 단위가 무엇인지까지 쓴다

### 3. core·vague 용어집을 읽는다 (항상)

용어집은 사용자 홈에 쌓는다. 플러그인 디렉토리는 업데이트할 때 덮어써지기 때문이다.
첫 줄의 복사는 매번 실행한다 — 이미 있는 파일은 덮어쓰지 않으므로 사용자가 쌓은 내용은
그대로 두고 플러그인 업데이트로 새로 생긴 도메인 파일만 추가한다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/ko-doc-write/scripts/init-style.py"
cat ~/.claude/ko-style/glossary-core.tsv
cat ~/.claude/ko-style/glossary-vague.tsv
```

**둘은 성격이 다르다.** core 는 구어체를 표준 용어로 바꾸는 치환이고(`앱` → `애플리케이션`),
vague 는 빠진 정보를 채우라는 지시다(`조용히 무시합니다` → `오류를 기록하지 않고 넘어갑니다`).
읽는 사람이 무슨 뜻인지 모르게 만드는 자리를 없애는 것이 vague 쪽 목적이라
**내부 문서와 대화 답변까지 전부 적용된다.**

종결어미·절 제목 형태는 `~/.claude/ko-style/sources.md` 의 「공통으로 확인된 형태」 절에 있다.
이건 주제와 무관하게 그대로 적용한다.

### 4. 도메인을 판정하고 용어집을 찾는다

```bash
ls ~/.claude/ko-style/domains/
```

파일이 있으면 읽고 5번을 건너뛴다. `sources.md` 의 실측일이 6개월 넘게 지났으면 다시 연다.

초기본에 든 도메인은 열이다 — `security` · `network` · `container` · `observability` ·
`database` · `storage` · `ci-cd` · `frontend` · `api` · `console-ui`. 여기 없는 주제(`payment` · `auth` · `ml` 등)면
새로 만든다. 한 문서가 두 주제에 걸치면 둘 다 읽는다.

### 5. 없으면 벤더 문서를 열어 수집한다

**한 번만 하면 다음부터 재사용한다.** 그 주제를 다루는 문서를 벤더마다 하나씩 고른다.

| 출처 | 도메인 | 성격 |
|---|---|---|
| NHN Cloud | `docs.nhncloud.com/ko` | 콘솔 조작·인프라 서술이 가장 촘촘하다 |
| 카카오클라우드 | `docs.kakaocloud.com` | 개념 설명과 규칙 서술. 영문 병기 방식이 명확하다 |
| 네이버 클라우드 | `guide.ncloud-docs.com` | 절차형 지시문. 종결은 `~해 주십시오` 다 |
| 토스페이먼츠 | `docs.tosspayments.com` | 개발자 대상 안내형. 경고 문구 형태를 여기서 본다 |
| Kubernetes 한국어 | `kubernetes.io/ko` | 인프라 개념어의 정본. 용어 심의를 거친 번역이다 |
| React·Vue 한국어 | `ko.react.dev` · `ko.vuejs.org` | 프론트엔드 용어와 튜토리얼 문체 |
| MDN 한국어 | `developer.mozilla.org/ko` | HTTP·웹 표준 용어 |
| Git 한국어 도서 | `git-scm.com/book/ko` | 버전 관리 용어 |

**쓰지 않는 출처** — GitHub Docs 한국어는 기계번역 품질이 낮아 제외했다.
AWS·Google Cloud·Azure 한국어도 문장 형태는 가져오지 않고 명사 용어를 대조할 때만 쓴다.
판단 근거는 `sources.md` 에 적혀 있다.

WebSearch 로 URL 을 찾고 WebFetch 로 연다. 프롬프트는 **원문 인용을 강제**해야 한다 —
요약을 받으면 정작 필요한 어휘가 사라진다.

```
이 페이지에서 아래를 원문 그대로 인용해 주세요. 요약하거나 바꿔 쓰지 마세요.
1) 모든 절 제목(헤딩)을 원문 그대로 나열
2) 사용자에게 무엇을 하라고 지시하는 문장 10개 — 종결어미까지 원문 그대로
3) <이 주제의 핵심 동작>을 서술한 문장 10개 — 원문 그대로
4) 주의·경고 박스의 문구 전부 — 원문 그대로
5) 이 문서가 쓰는 한국어 명사 용어 목록
```

3번의 `<핵심 동작>` 을 주제에 맞게 바꾼다. 보안이면 "차단·허용·권한 부여", 관측이면
"수집·보관·집계", 데이터면 "적재·조회·백업" 처럼.

### 6. 치환 쌍을 용어집에 적는다

수집한 표현과 내가 쓰려던 표현을 대조해 다른 것만 남긴다.
`~/.claude/ko-style/domains/<도메인>.tsv` 에 탭으로 구분해 적는다.

```
## <도메인> 도메인. <무엇을 다루는 문서에 적용하는지>
## 컬럼: type <TAB> pattern <TAB> replacement <TAB> source <TAB> note
## 실측: <벤더 문서 이름들> (<날짜>)
noun	비번	비밀번호	토스·NHN
raw	뚫린다|뚫렸|뚫려	침해됩니다	실측 문서 전체에서 0건
```

- `noun` — 명사. `ko-lint.py` 가 한글 조사 경계를 자동으로 붙인다
- `raw` — 정규식 그대로. 용언은 활용형을 `|` 로 나열한다 (`막는다|막습니다|막아 준다`)
- `source` 는 반드시 채운다. **외부 공개 문서만 출처로 쓴다** — 사내에서 쓴 문서는 그것도
  AI 가 쓴 것이라 기준이 되지 못한다. 어디에도 안 쓰이는 표현이면 `실측 문서 전체에서 0건`
- 자연스러운 용법과 겹치는 표현은 넣지 않고 `note` 에 뺀 이유를 적는다
- 넣기 전에 작업 중인 레포지토리의 `docs/**/*.md` 에 패턴을 돌려 적중 건을 훑는다. 정상 용법이 걸리면 패턴을 좁힌다

`sources.md` 에 열어 본 URL 과 날짜를 추가한다.

### 7. 그 표현으로 쓴다

수집한 형태를 지킨다.

- 서술은 `~합니다`, 지시는 `~하세요`. **한 문서 안에서 섞지 않는 것이 규칙이고 어느 쪽을
  고를지는 문서 성격이 정한다.** 실측 결과가 둘로 나뉘었다 — 국내 클라우드 4사·토스·React·Vue·MDN 은
  경어체, Kubernetes 한국어와 Git 한국어 도서는 해라체다. 레퍼런스·개념 문서는 해라체,
  사용자 가이드·튜토리얼은 경어체를 쓴다. 레포지토리에 이미 정한 문체가 있으면 그것을 따른다
- 1인칭·의문형 제목을 쓰지 않는다
- 경고는 조건 → 결과 → 할 일 순서로 담담하게. 느낌표와 `절대` 를 쓰지 않는다
- 체크리스트 도입부에 범위 한정을 넣는다 (모두 확인해도 보장되지는 않는다는 문장)
- 항목은 산문 한 단락으로 쓰고 확인 방법은 하위 항목으로 뺀다
- 명칭은 정식 명칭 — 애플리케이션 · 프론트엔드 · 레포지토리
- **무엇이 / 어떤 조건에서 / 어떻게 되는지를 나눠 쓴다.** 부사로 얼버무리지 않는다.
  벤더가 쓰는 형태를 그대로 따른다 — `image pull이 실패합니다` · `해당 키가 무시되는 일이
  있을 수 있다` · `Effect는 client 환경에서만 동작합니다. 서버 렌더링에서는 동작하지 않습니다.`

토스 가이드 「문장 다듬기」에서 가져온 규칙이다. 앞의 셋은 용어집 패턴으로도 걸린다.

- **메타 담화를 뺀다** — `앞서 설명했듯이` · `아시다시피` · `이제 알아보겠습니다` 없이 그 내용만 쓴다
- **명사 대신 동사로** — `코드 최적화 진행 후 배포 수행이 필요합니다` → `코드를 최적화한 후 배포하세요`
- **범위를 이름으로** — `일부 브라우저에서` → `Internet Explorer에서`. `많을 때` → `10,000건을 넘으면`
- **한 문장에 생각 하나** — `요청 헤더를 포함해야 하며, 올바른 인증 정보를 제공해야 정상적으로 응답을 받을 수 있습니다` → `요청 헤더와 인증 정보를 포함하세요`
- **누가 · 무엇을 · 어디에** — `파일을 업로드하면 자동으로 저장됩니다` → `사용자가 파일을 업로드하면 서버에 자동으로 저장됩니다`.
  `로그를 확인하세요` 에는 경로(`/var/log/app/error.log`)를 붙인다
- **앞뒤 참조를 밝힌다** — 뒤에서 쓸 값을 처음 만들 때 어디서 쓰는지, 앞에서 만든 값을 다시 쓸 때 어디서 만들었는지 링크와 함께 쓴다
- **독자가 주어** — 절차 문장은 `이 라이브러리는 초기화를 수행해요` 가 아니라 `이 명령어를 실행하면 데이터베이스를 초기화할 수 있습니다`.
  도구의 동작 자체를 설명할 때는 도구가 주어가 된다(`kubelet 이 컨테이너를 재시작합니다`)
- **능동형** — `설정이 완료되어야 합니다` → `설정을 완료하세요`
- **업계 은어를 동작으로** — `서버를 찔러서` → `서버에 요청을 보내서`
- **약어는 처음 나온 자리에서 풀어 쓴다** — `SSR(Server-Side Rendering)`. 약어와 괄호 사이는 띄우지 않는다.
  API·URL·HTTP 처럼 독자가 이미 아는 약어는 풀지 않는다
- **같은 개념은 같은 말로** — 한 문서에서 `추가` · `첨부` · `넣다` 를 섞지 않는다. `상태` 를 `데이터 저장` · `값 유지` 로 바꿔 부르지 않는다.
  기술 이름은 공식 표기(`Kubernetes` · `JavaScript`)를 쓴다

### 8. 자가 점검

**구조** — 목차 규칙을 지켰는지 본다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/ko-doc-write/scripts/structure-check.py" <대상 문서>
```

H4 이하 제목 · 첫 제목 아래 개요 유무 · 30자 넘는 제목 · 물음표·느낌표 제목 ·
같은 수준 제목 형태가 섞인 곳 · 풀어 쓰지 않은 약어를 목록으로 낸다. 판정이 아니라 목록이다 —
표 제목에 식별자가 들어가 길어진 것, 독자가 이미 아는 약어는 그대로 둔다.
그다음 `references/doc-types.md` 의 그 유형 체크리스트를 한 번 대조한다.

**지어낸 표현** — 그 문서에만 있고 같은 저장소의 다른 문서엔 한 번도 안 나오는 어절로 찾는다.

```bash
python3 - <<'PY'
import pathlib, re, sys
target = pathlib.Path("<대상 문서>")
root = target.parent.parent           # 비교할 문서 묶음의 뿌리
strip = lambda t: re.sub(r"```.*?```", " ", t, flags=re.S)
words = lambda t: set(re.findall(r"[가-힣]{2,}", strip(t)))
mine = words(target.read_text(encoding="utf-8"))
other = set()
for p in root.rglob("*.md"):
    if p != target:
        other |= words(p.read_text(encoding="utf-8"))
only = sorted(mine - other)
print(f"이 문서에만 있는 어절 {len(only)}개")
print(", ".join(only))
PY
```

나온 목록을 훑어 지어낸 표현을 찾는다. 실제로 이 방법이 "그 기능이 멈추는 자리" ·
"행선지가 갈립니다" · "짜고 오면 늦다" 를 잡아냈다.

python3 "${CLAUDE_PLUGIN_ROOT}/skills/ko-doc-write/scripts/ko-lint.py" <대상 문서>

용어집·문장 규칙(번역투·이중 피동·결산 상투구 등)·종결어미 일관성·제목 형식을 본다.
