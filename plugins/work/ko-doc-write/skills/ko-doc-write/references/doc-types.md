# 문서 유형과 템플릿

출처: 토스 테크니컬 라이팅 가이드 「문서 유형 정하기」 (https://technical-writing.dev/type/, 2026-09-29 실측).
템플릿 절 제목은 가이드 원문을 그대로 쓰고 안내 문장만 우리 종결(`~합니다`·`~하세요`)로 바꿨다.

## 유형은 독자가 문서를 연 목적이 정한다

| 유형 | 독자가 문서를 여는 때 | 하위 형태 |
|---|---|---|
| 학습 | 새 기술·도구를 처음 접해서 흐름을 익히고 싶을 때 | 시작하기 · 튜토리얼 |
| 문제 해결 | 배경 지식은 있고 특정 작업을 하거나 특정 문제를 풀고 싶을 때 | How-to 가이드 · 트러블슈팅 |
| 참조 | 동작은 알고 있고 특정 기능·API 의 세부 사항을 찾아 적용하고 싶을 때 | API 레퍼런스 · 에러 코드 목록 |
| 설명 | 개념·원리·배경을 깊이 이해하고 싶을 때 | 개념 문서 · 도메인 문서 |

판별 질문 — 독자의 첫 질문이 어떤 모양인지 본다.

- 「X 를 처음 써 보는데 어떻게 시작하나요」 → 학습
- 「X 에서 Y 를 설정하려면」 → 문제 해결 (How-to)
- 「Z 에러가 나요」 → 문제 해결 (트러블슈팅)
- 「이 함수의 options 에 뭐가 들어가나요」 → 참조
- 「X 는 왜 이렇게 동작하나요」 → 설명

**하위 형태 둘의 차이**

- 시작하기는 전체 흐름과 필수 개념을 보여 준다. 튜토리얼은 명확한 목표와 결과물이 있고 따라 하면서 개념을 익힌다. 설치·설정이 아주 짧으면 튜토리얼 앞부분에 시작하기를 합친다.
- How-to 가이드는 특정 기능을 구현하는 절차다. 트러블슈팅은 이미 발생한 문제를 진단하고 해결하는 과정이다.
- 에러 코드 문서는 「이 에러가 무슨 뜻이지」를 찾는 사전이고 트러블슈팅은 「어떻게 해결하지」를 찾는 가이드다.

**유형은 섞어도 된다.** 학습 문서 안에 필요한 개념 설명을 짧게 넣는 식이다. 다만 한 페이지의 주된 유형은 하나로 정한다. How-to 가이드와 참조 문서가 둘 다 필요하면 페이지를 나누고 서로 링크한다.

## 1. 학습 문서

지킬 것

- 처음부터 끝까지 막힘없이 따라 할 수 있어야 한다. 모든 예제 코드는 실제로 실행해 본 것만 싣는다
- 단계별로 쓴다. 예제는 간단한 것에서 시작해 점점 어렵게 한다
- 실행할 수 있는 코드를 넣는다. 단계마다 성공했을 때 보이는 결과를 적어 독자가 스스로 확인하게 한다
- 흐름은 목표 → 준비 → 실습 → 적용 → 확장 순서다
- 본문은 성공 경로만 다룬다. 자주 막히는 지점은 끝의 FAQ 로 보내고, 부가 설명·심화 내용은 접어 둔다(`<details>`)

```markdown
# [튜토리얼 제목]

[이 튜토리얼을 마치면 독자가 무엇을 할 수 있는지 한두 문장으로 씁니다.]

## 목표
[따라 하고 나면 달성할 목표를 목록으로 씁니다.]

## 사전 요구사항
- [필요한 사전 지식과 설치할 도구. 버전을 적습니다. 없으면 절을 뺍니다.]

## 1단계. [첫 번째 단계 제목]
[이 단계에서 할 일과 이유를 쓰고 코드나 화면을 넣습니다.]
[성공하면 무엇이 보이는지 씁니다.]

## 2단계. [두 번째 단계 제목]

## 최종 결과 확인
[목표를 달성했을 때 나오는 결과를 씁니다.]

## FAQ
```

체크리스트

- 학습 목표를 명확하게 제시했는가
- 직접 따라 해 봤을 때 오류가 나지 않는가
- 단계별로 설명했는가
- 독자가 직접 실행할 수 있는 코드 예제가 있는가

## 2. 문제 해결 문서

지킬 것

- 문제 상황을 정의한다. 원인과 현상을 나눠 쓰고 에러 메시지·로그를 원문 그대로 넣는다
- 바로 적용할 수 있는 해결 방법을 준다. 명령어·코드·설정을 넣고 그 방법이 왜 문제를 푸는지 한 문장 덧붙인다
- 환경별 차이를 다룬다 (OS · 라이브러리 버전 · 클러스터 종류)
- 트러블슈팅은 가장 흔한 원인부터 확인하게 배치한다. 선택 단계는 제목에 `[선택]` 을 붙인다
- 끝에 문제가 해결됐는지 확인하는 방법을 둔다

```markdown
# [문제 해결 문서 제목 — 에러 이름이나 작업 이름을 넣습니다]

[이 문서가 어떤 문제를 해결하는지 한두 문장으로 씁니다.]

## 문제 정의
[독자가 겪는 상황과 에러 메시지를 씁니다.]

## 사전 요구사항
[필요한 환경이나 조건. 없으면 절을 뺍니다.]

## 해결 방법
### [첫 번째 해결 방법]
### [두 번째 해결 방법]

## 문제 해결 후 확인 방법
[해결된 뒤의 모습이나 확인 명령을 씁니다.]
```

체크리스트

- 에러 원인만이 아니라 그 에러를 이해하는 데 필요한 기본 지식을 줬는가
- 즉시 적용할 수 있는 해결 방법이 있는가
- 환경별 차이를 다뤘는가

## 3. 참조 문서

지킬 것

- 정확하고 완전해야 한다. 빠진 항목·모호한 설명이 없고 최신 상태여야 한다
- 항목마다 같은 구조로 쓴다 (이름 → 매개변수 → 반환 값 → 예제)
- 찾기 쉽게 만든다. 주제별로 절을 나누고 목차와 앵커 링크를 둔다
- 참조 문서를 쓰기 전에 알아야 할 것(API 키 · 인증 방식 · 요청 헤더)은 앞부분에 둔다
- 개요에는 기능만이 아니라 그 요소를 쓰면 무엇을 할 수 있는지를 쓴다

```markdown
# [참조 문서 제목]

## 개요
[이 요소가 무엇이고 언제 쓰는지, 쓰면 무엇을 할 수 있는지 씁니다.]

## 속성 및 옵션
| 속성명 | 타입 | 기본값 | 필수 | 설명 |
|---|---|---|---|---|

## 시그니처

## 반환 값

## 사용 예제
[어떤 상황에서 쓰는지와 함께 예제를 넣습니다. 기본 사용법부터 씁니다.]

## 주의 사항
```

체크리스트

- 검색과 탐색이 쉬운 구조인가
- 정보가 정확하고 완전한가
- 모든 항목이 같은 구조와 형식인가
- 실제로 쓸 수 있는 예제 코드가 있는가

## 4. 설명 문서

지킬 것

- 기술이 등장한 배경과 해결하려는 문제를 먼저 쓴다
- 동작 방식을 단계별로 쓴다
- 다른 접근 방식과 비교하고 장단점을 쓴다
- 구조·데이터 흐름은 도식이나 표로 보여 준다
- 도메인 문서는 구성 요소 정의 → 사용자 행동 흐름(예외 상황 포함) → 흐름도 순서로 쓴다

```markdown
# [개념명]

## 개념 소개
[이 개념이 무엇인지 짧게 씁니다.]

## 등장 배경
[왜 등장했고 어떤 문제를 해결하는지 씁니다.]

## 동작 방식

## 활용
[실제 프로젝트에서 어떻게 쓰이는지 씁니다.]
```

체크리스트

- 핵심 원리와 배경을 명확하게 설명했는가
- 복잡한 개념을 도식으로 보여 줬는가
- 선행 지식을 안내했는가

## 여러 페이지 문서의 구조

문서 묶음을 새로 만들 때는 왼쪽 내비게이션 메뉴를 먼저 짠다고 생각한다.

```
docs/
├── get-started.md      # 시작하기
├── tutorials/          # 학습
├── how-tos/            # 문제 해결 — 특정 기능 구현 · 특정 목표 달성
├── explanations/       # 설명
├── reference/          # 참조 — API · 에러 코드 목록
├── troubleshooting.md  # 에러 해결 가이드
└── glossary.md         # 용어 사전
```

- 학습 문서는 전체 흐름으로 시작해 실습 · 심화 순으로 계층을 둔다
- 문제 해결·설명 문서는 단계 없이 같은 수준에 나란히 둔다
- 참조 문서는 목록 페이지를 따로 둔다
- 여러 개념을 개략적으로 소개해야 하면 개요 페이지를 만들고 각 문서로 링크한다
- 튜토리얼에서 짧게 다룬 내용은 가이드·참조 문서로 크로스링크한다

기존 저장소에 문서를 넣을 때는 그 저장소의 디렉터리 규칙(RND-INFRA `docs/guide/` 등)을 먼저 따른다. 위 구조는 새로 만드는 묶음에만 쓴다.
